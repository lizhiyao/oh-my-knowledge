# SDK 案例：知识变化后，核对引用它的载体

本页冻结案例展示 2026-10-14 已验收的知识维护链路：关联后续来源、限定旧说法的适用场景、修订或舍弃知识，再核对和更新载体。材料来自 sentry-miniapp 的既有 SDK 验收；当时的 OMK 实现读回独立副本，并在 Studio 打开 v4／v5 核对。

截图与 v4／v5 身份属于此前的知识契约。当前正文主数据版本不直接读取旧工作区；请按[知识维护动线](extract-knowledge.md)显式迁入全新目录，核对新的 pending 正文并重新作保留决定。旧载体和组织引用只归档，不自动重定向。旧身份与截图本身不证明当前正文流程已验收，也不能仅凭包版本号推断数据兼容；当前契约的独立读回见下节。

第一次使用先按[知识维护动线](extract-knowledge.md)建立自己的工作区。本页用于理解具体结果，不要求你安装 SDK 或调用模型。

## 当前正文契约下的闭环（2026-10-29）

[#1174](https://github.com/lizhiyao/oh-my-knowledge/issues/1174) 在全新本地工作区实际运行生产知识应用、存储适配器和 Codex 提炼流程。输入为忠实恢复的两个选定脱敏历史窗口、人工静态观察，以及本轮真实测试工具记录；没有恢复完整原会话，也没有续跑已丢失的旧载体任务身份。三个提炼来源生成6条完整正文，正文与关联两阶段各调用模型一次。来源核对保留了旧报告、未知版本与静态观察的限定。

本轮由 Agent 明确保留其中5条，首次载体 v1 引用这5条；#428 业务验收条目继续 pending。随后用固定 SDK 快照的实际测试结果补充一条正文：4个现有测试文件共52项通过，仅覆盖 Node／in-memory transport。新修订先回到 pending，旧 retain 仍绑定旧修订，再由 Agent 明确保留新修订。Agent 维护决定不代表人工 Gold；载体中的验证状态仍为 `not_assessed`。

| 读回项 | 实际结果 |
|---|---|
| 新载体 v2 | 沿用3条、替换1条、移除1条；被移除的历史修复报告仍保留在知识库。 |
| 精确引用 | v1 保留旧修订并提示1项变化；v2 引用所选当前修订，变化提醒为0。 |
| 内容与资产 | v1 全部文件字节不变；手工正文、自定义 metadata 值和4个分发资产保留。 |

[当前契约读回记录](../../../public/sdk-body-closure-evidence.json)提供两个载体的完整身份、正文校验摘要与精确知识引用，并单独记录任务比较。完整知识正文、原始返回和执行诊断保存在本地，不随本页公开。新旧载体主 Markdown 分别为43,077与39,659字节，未按8KB裁剪。

任务比较沿用两道 SDK 审查题、原布尔／路径验收程序和7个固定源码文件，两个版本各运行一次。测量的是提供主 Markdown 的消费路径；四个资产的保留已单独核对，原生 Skill 自动发现和资产读取不在该比较范围。v2 同时补充运行证据并移除已被替代的报告，不能将结果归因于单一知识条目。实际结果与成本以读回记录为准，少量已暴露题目不证明普遍知识收益；[#1115](https://github.com/lizhiyao/oh-my-knowledge/issues/1115)继续独立跟踪收益研究。

实际4个模型执行与4个本地验收均成功，无重试；v1／v2 均为2题通过，未观察到通过率提升。整组约9分12秒，执行器记录输入904,770 tokens（其中缓存输入771,712）、输出2,538 tokens；这些是多次 Agent 交互的累计用量，不是单次 prompt 长度。美元费用未上报，记为未知。另有6次正文／关联生成，约6分钟，输入123,821、输出24,485 tokens；维护和载体保存没有新增模型调用。

## 历史材料与范围（2026-10-14）

- 对象是本项目的 `@sentry/core` 组件；版本是观察条件，不自动成为另一个组件身份。
- 历史窗口包含 protected 覆写与 Session 隔离的讨论。旧说法保留为历史记录，不能直接当成当前未解决缺口。
- 后续观察冻结 [SDK 源码 30ffb003](https://github.com/lizhiyao/sentry-miniapp/commit/30ffb0030376e63a943f5d69beced539c7810171)，记录 `@sentry/core 11.6.0` 的依赖、源码接缝和测试源码。它是人工整理的静态材料，没有执行 SDK 动态测试。
- 维护验收记录见 [#1166](https://github.com/lizhiyao/oh-my-knowledge/issues/1166)；知识变化提醒和更新核对见 [#1168](https://github.com/lizhiyao/oh-my-knowledge/issues/1168)。本次副本读回未改写原始 27 份文件，没有新增模型调用。

## 从来源到新载体

| 环节 | 案例中的实际变化 | 应核对什么 |
|---|---|---|
| 持续积累 | 人工确认后，core 对象的来源窗口成员从 2 个增至 3 个。 | 来源与对象含义；同名不自动归并。 |
| 旧知识修订 | 将旧修正要求限定为历史场景；新修订重新作保留决定。 | 原文、适用条件、未知和修订理由。 |
| 停止沿用 | 舍弃“历史公开接口缺口说法（原窗口版本未知）”。 | 舍弃保留历史，不让它进入当前使用载体。 |
| 补充条件 | 静态知识明确“只证明源码，不证明动态通过”。 | 保存测试源码不等于执行测试通过。 |
| 变化提醒 | 历史 v4 仍引用三条知识，其中两条需复核。 | 当前新修订与保留状态；提醒不判断真伪或语义过时。 |
| 明确更新 | v5 选择两条当前保留知识，沿用一条、替换一条、移除一条。 | 本次引用变化、正文、精确修订和依赖资产。 |
| 历史回看 | v4 的旧正文和三条引用继续可读；v5 的引用检查为零项变化。 | “没有引用变化”不等于内容正确或效果已验证。 |

[冻结读回记录](../../../public/sdk-maintenance-evidence.json)保存观察时间、OMK 运行时 commit、载体身份与 v4／v5 的完整修订身份，也记录来源可用状态和对象历史成员数（2 → 1 → 2 → 3）。期间解除再重新关联的历史保留，随后接入第三个来源窗口。

| 知识 | 历史 v4 | 当前 v5 |
|---|---|---|
| 历史 protected 覆写与 Session 审查 | 引用修订 `1009571e` | 沿用同一精确修订 |

## 历史 Studio 核对记录

以下步骤记录 2026-10-14 在旧契约下的验收操作，不用于在新迁入工作区重放这些旧身份；新工作区应先核对新正文并明确生成新载体。

1. 打开知识库，查看对象的来源成员，再从知识条目回到原文。候选先核对条件与证据，按理由保留或舍弃。
2. 打开已保存载体，从版本选择进入历史 v4，再进入“变化核对”。案例中的两项提醒分别来自知识修订和不再保留。
3. 展开变化，比较“载体引用的旧修订”与“知识当前修订”，核对标题、陈述和条件；按引用进入对应知识详情。
4. 回到当前版本，选择“生成新版本”，逐项确认沿用、替换和移除，再明确保存。这里只更新本次选择的知识区；手工内容与依赖资产保留。
5. 重新读取最新载体，核对正文和“知识引用”；再切回历史版本，确认旧内容仍然可读。只有需要验证任务效果时，再从明确版本进入评测。

![2026-10-14 旧知识契约下 SDK v4 的 Studio 变化核对阅读区](../../../public/sdk-maintenance-review.png)

截图记录当时中文案例的真实阅读区，展示历史引用与当时最新知识的核对；它既不是新一次模型提取结果，也不是当前正文主数据契约的验收。截图中的版本和时间属于该冻结案例。

来源缺失、读取失败或载体被外部修改时，先检查提示并重新读取，不能把失败当成没有变化。检查只覆盖这个版本已引用的知识，不覆盖尚未引用的新知识。完整行为边界见[知识维护契约](../../specs/knowledge/knowledge-maintenance.md)。

## 历史证据支持什么

支持持续维护、修订与精确引用的可回查链路：v4 的历史三条引用保留，v5 只引用所选的两条当前修订，正文与保存清单一致。

没有证明 SDK 升级后动态行为正确、节省时间、跨 Agent 自动复用或每条知识的独立贡献。它使用已暴露材料和作者复核，人工记录适配器不计作自动提取成功。[知识收益研究](https://github.com/lizhiyao/oh-my-knowledge/issues/1115)继续单独记录实际使用与收益。
