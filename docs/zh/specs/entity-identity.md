# 实体身份规则（设计草案）

状态：本稿定义 [Issue #1127](https://github.com/lizhiyao/oh-my-knowledge/issues/1127) 的身份规则与正反例。P2 实现 §8 已批准契约；P3 界面完善与 P4／P5 独立标注、模型验收待完成。当前实现以[实体提取规范](./entity-extraction.md)为准。

本稿沿用[知识的概念定义](../explanation/knowledge.md)：实体是知识描述的事物，知识表达它在特定上下文中的状态、关系或行为。规则由 OMK 自主实现，借鉴成熟设计，不要求引入第三方记忆框架、图数据库或额外模型。

## 1. 用户需要从实体找到什么

实体提取应帮助人和 AI 回答以下问题，而不是尽可能列出所有名词：

| 使用场景 | 应能得到的结果 | 身份错误的后果 |
|---|---|---|
| 查某组件的经验 | 找到测试和生产的不同表现，并读到各自的条件与证据。 | 误合并部署对象或丢失条件，把局部成功当作整体成功。 |
| 查具体部署的故障 | 明确是哪一个实例、何时发生、哪些修复仍未验证。 | 把另一个实例的成功或修复移用过来。 |
| 找改名后的文件 | 有改名依据时沿同一文件追溯旧名称与关联知识。 | 改名产生重复对象，或同路径的新文件继承旧文件知识。 |
| 区分计划与结果 | 分别找到计划要求、实际执行及已观测结果。 | 把“准备做”当作“已经做完”。 |
| 核对“它／它们” | 回到原文，看得到指代依据、集合成员或身份缺口。 | 任取一个对象，或把集合中的共同描述错误分配给个体。 |

本阶段的身份边界仍是一份不可变来源窗口及其分析修订。工作区检索可以同时展示多个窗口的同名对象；它们不因此成为一个跨窗口身份。跨 Agent 管理知识是产品方向，自动跨 Agent 消歧不在本稿范围内。

## 2. 判定流程与基本规则

按以下顺序判断每处值得保留的提及：

1. 保留来源原文与位置，先确认它谈的是事物、属性值还是一项陈述。数值、环境词、失败状态不必独立成为实体。
2. 判断原文所指的层次：组件、明确的版本对象、部署实例、文件、计划、执行活动或集合。只选择来源支持的粒度，不补造更具体的对象。
3. 只在有对应依据时复用窗口内的身份：明确的别名／改名、带来源命名空间的标识，或可解释的上下文共指。外部标识还需说明所属项目、系统及可见的有效范围；不能假定它永不复用。
4. 来源明确区分的对象必须分开。名称、类型、路径、字符串／向量相似度只能帮助找候选，不能单独证明同一身份。
5. 无法确定指向哪个对象时，保留一个未消解对象及理由；有明确候选时保留候选，不任取一个。身份已知而环境、版本或结果未知时，保留该身份，在陈述中说明未知条件。
6. 全窗口核对晚到的澄清和纠正，再绑定知识的主体／对象及上下文。新分析或纠正不得回写旧修订。

模型负责语义判断；程序负责原文定位、身份与引用闭合、修订绑定等确定性检查。结构通过不证明消歧正确；相同文本出现两次，也不证明两处提及属于同一对象。

## 3. 组件、版本与部署实例

**组件身份默认表示来源持续讨论的系统或模块。环境、版本和时间通常限定陈述，不自动创建新实体。** 当来源明确讨论可分别指向的部署、实例或版本对象时，为它们建立独立身份；组件与实例的关系须有来源依据，不能靠同名推导。

| 来源表达 | 应采用的身份与陈述 | 不应采用的处理 |
|---|---|---|
| “Harbor 使用 Quartz 调度器。测试环境中 Quartz 通过；生产环境中 Quartz 报错，修复未验证。” | 一个 Quartz 组件；测试通过、生产报错、生产修复未验证分别保留条件。 | 仅因环境不同强制拆出实例，或省略生产条件，写成“Quartz 已通过”。 |
| “Quartz 的测试实例 T 通过；生产实例 P 报错。它们部署在不同环境。” | T、P 是两个实例；有组件提及时保留 Quartz 组件，来源支持二者属于该组件。 | 把 T、P 合并，或以抽象组件替代明确的实例指代。 |
| “T 已升级到 v2，仍是昨天那个实例。” | T 身份延续；升级前后版本和状态属于不同时间、条件下的陈述。 | 每次升级都为 T 重新分配身份，丢失连续历史。 |
| “对比 Quartz v1 与 v2 的发布包；这两个包分别归档。” | 两个明确的版本对象；组件身份与包身份分开，包的版本固定。 | 把两个不可变发布包合并；或将一次比较推广成所有版本都必须是实体。 |
| “Quartz 通过了，但记录没说在哪个环境。” | 已知所谈组件时保留 Quartz；环境未知，成功范围有限。 | 为未知环境制造“未知 Quartz 实例”，或把成功应用到生产。 |
| “T 和 P 都叫 Quartz。它报错了，暂时不知道是哪一个。” | T、P 分开；“它”属于一个未消解实例，候选为 T、P。 | 选择最近出现的 P，或把实例歧义隐藏到抽象组件上。 |

“生产 Quartz”这一短语本身不足以决定粒度：上下文在描述组件的生产表现时沿用组件；已建立生产部署指代时引用那个实例。两者无法区分且会影响知识归属时，显式保留粒度不确定性，不能悄悄改成更抽象或更具体的对象。

**组件与实例不是可随意互换的主语。** “实例 P 失败”可以帮助用户从组件找到相关经验，但不能自动成为“组件所有实例都失败”。检索到相关对象的知识与将主张推广到相关对象，是不同动作。

组件／实例和组件／版本的关联是本稿要求保留的语义；P2 通过 §8 明确版本化关联字段；完整关联操作与检索由 P3 补齐。

## 4. 集合、未知身份与提及位置

**集合是一个共同指代的对象；未知身份是不知道指向哪个对象。** 两者不能用一个笼统的“未知”标签替代。

| 来源表达 | 应保留的结果 | 不应采用的处理 |
|---|---|---|
| “Aster 和 Birch 是两个服务。它们都启动了。” | Aster、Birch 分开；“它们”是一处集合提及，成员为二者；“都”支持分别陈述二者启动。 | 将同一个“它们”位置复制成两个个体提及。 |
| “Aster 和 Birch 协同完成任务，耗时十秒。” | 共同参与的集合／活动及整体结果；来源未给出每个服务的耗时。 | 给每个服务各写“完成任务耗时十秒”。 |
| “Atlas 和 Beacon 之一报错了，它尚未修复。” | 一个未消解对象；可能身份为 Atlas 或 Beacon。 | 建立确定的 Atlas＋Beacon 集合，把二者都标成报错。 |
| 截断窗口只剩“它们还未确认。” | 保留未消解的复数指代、成员未知及窗口限制。 | 虚构成员，或当作已知单个实体。 |

已知集合可以保留部分已知成员与成员缺口；不能把不完整成员表当作全集。候选必须属于相同指代层次：“它们”可能指不同组合时，不能将单个 A、B 填成两个可任选的单体候选。候选组合无法有据表达时，保留文字说明与未知，不编造没有提及依据的集合身份。

每处接纳的原文位置只对应一条提及。集合提及、成员关系和由“都”支持的个体陈述分别表达，不能靠重复位置完成分发。当前重复位置拒绝规则保持；§8 定义集合成员、复数歧义和个体陈述的证据绑定；结构测试不证明模型提取质量。

引用使用原文连续短语；重复文本须明确零起始出现序号，重叠匹配也计数，唯一匹配可省略。宿主拒绝歧义位置，不模糊匹配或任选第一处。UTF-16 位置仍由宿主计算；§8 替换旧的前后文引用方式。

## 5. 改名、复制、计划与执行

| 来源表达 | 身份规则 | 需要保留的边界 |
|---|---|---|
| “项目 A 的 a.md 改名为 b.md，仍是同一文件。” | 延续文件身份，保留有依据的旧名／新名和时间。 | 不改写旧修订里的名称或位置；不推断功能变化。 |
| “项目 B 也有 b.md。” | 与项目 A 的文件分开。 | 同路径、同内容或同类型不构成跨项目身份依据。 |
| “删除旧 b.md 后，在原路径新建了另一个文件。” | 旧文件与新文件分开，即使路径相同。 | 路径是定位信息，不是永久身份。 |
| “把 a.md 复制为 b.md，两个文件均保留。” | 两个文件身份；复制关系有来源支持。 | 不能把复制当改名或把相同内容当同一文件。 |
| “BuildKit 写出 build.log；它下次还会覆盖这份日志。” | 工具与日志分开；按上下文确认“它”指工具。 | 不把日志中的工具名、命令或攻击文本自动当作当前操作。 |
| “R1 是发布计划；D1 是按 R1 进行的测试演练，生产发布尚未开始。” | 计划 R1、执行活动 D1 分开；可有来源支持的执行依据关联。 | 测试演练成功不证明生产发布完成，也不证明计划有效。 |
| “明天再按 R1 演练一次 D2。” | R1 仍是计划，D2 是另一项计划中的执行活动。 | 把 D2 与 D1 合并，或把未来活动记录成已经发生。 |

时间和版本变化本身不决定新身份。有明确连续性时保留身份与不同时段的状态；有替换、复制或另一次执行的依据时分开；连续性证据不足时保留不确定性。计划、规则和概念可作为实体，但其中的要求、适用范围、行为与结果仍需作为有证据的知识陈述。

## 6. 晚到纠正、存储与展示要求

来源说“刚才说错了，报错的是生产 Quartz，不是 Cedar”时，分析应按明确纠正重新判断相关指代，保留前一说法及纠正依据。纠正某个对象的名称／归属，不会证明其报错、修复或成功结果是真的。不同说话者的相互矛盾也不等于后一条自动胜出；无法裁决时保留冲突与来源。

存储和展示在后续实现中须做到：

- 分开显示对象标签、指代层次、身份依据、限定信息、成员／相关对象及未知项；不能用一段描述承担全部信息。
- 名称是检索入口；分析／实体／修订身份才是当前窗口绑定。同名对象在目录里分开展示，使用来源和限定帮助区分。
- 组件与实例、集合与成员的关联只表示原文支持的关系；不自动合并知识、转移结果或计算因果收益。
- 新分析保留父修订、理由与原始证据；现有知识继续绑定生成时的明确修订。把纠正用于知识须创建新知识修订，用户仍可查看旧绑定。
- 拆分后不能任选一个新对象继承旧知识主语。来源不可用、成员不完整或关联知识读取失败，应分别展示限制，而不是“没有对象／没有知识”。

这些要求补充[修订与存储边界](./entity-extraction.md)。§8 明确已批准的版本替换及存量影响，不添加兼容 reader、自动迁移或持久索引。

## 7. 从规则进入实现与验收

本稿示例是设计用正反例，**不是独立裁决的 gold，也不是提取能力已经改善的证据**。P1 的完成仅代表有了可审查的身份规则。后续按以下边界推进：

| 阶段 | 交付与判定 |
|---|---|
| P2 契约与接纳 | 把以上语义落实到必要的版本化契约、提取提示词及程序校验；处理集合重复提及、引用前后文和案例角色等已知失败。 |
| P3 存储与展示 | 复用当前存储、Studio 和 CLI，验证新语义的纠正、历史绑定、检索与失败路径。 |
| P4 标注与工具 | 独立复核身份与提及规则，冻结允许的语义表达、关键覆盖和误合并／误拆分标准；区分采集失败、结构拒绝与可选结果未出现。 |
| P5 模型验收 | 在新的数据与调用授权下运行；保留全部结果、用量及限制，分别报告合成回归与独立复核的真实记录。 |

验收不能只比较实体数量：需检查对象层次、必要的身份分离、共指依据、集合／未知表达、知识主体／对象与条件，以及纠正后的修订绑定。关键提及和应有身份须在输出前标注；不能只检查模型返回的对象，也不能让模型省略实例以规避误合并。

允许同义标签和有来源支持的额外对象，不允许用抽象组件替代明确实例、将集体结果分配给个体，或丢失影响复用的条件。组件粒度的跨环境陈述可以合格，前提是来源没有建立必须分开的实例且条件完整；独立复核须按这些规则判定，而不是按返回 ID 数量判定。

[两轮历史报告](../explanation/entity-extraction-repeat-quality.md)及冻结证据保持原样。它按当时冻结的实例标准未通过；本稿不回头改 gold、提高历史分数或重算旧结果。新的身份规则、标注与检查程序须使用新的测量身份，才能报告后续质量。独立复核和新的模型验收尚未执行。

## 8. P2 契约与替换方案（已批准）

2026-10-10 已批准本节的替换方案。P2 实现身份契约、提示词与接纳、身份映射、写入恢复及纠正传递；P3 的完整关联操作和 P4／P5 的独立质量验收仍待完成。

### 8.1 最小身份结构

在现有实体上增加三个必填字段，不建立第二份全局对象库：

| 字段 | 语义与校验 |
|---|---|
| `referentKind` | `object`、`component`、`instance`、`version`、`collection`、`plan`、`activity`；普通人、文件、工具、规则和概念可用 `object`。这是指代层次，不是可信度。 |
| `componentRef` | `null`，或包含 `entityId`、`mentionIds`、`rationale` 的关联。只允许实例／版本关联一个已提出的组件；目标和提及须属于本分析，至少一处提及属于该实例／版本。未建立组件身份时为 `null`，不按名字补造。 |
| `collection` | 非集合为 `null`；集合包含 `memberEntityIds`、`completeness`、`mentionIds`、`rationale`。完整性为 `complete`、`partial` 或 `unknown`；提及中至少一处属于该集合。成员引用不重复、不悬空、不形成直接或间接自包含。 |

集合成员完整性与身份消歧分开：已知集合可以有成员缺口，仍为 `proposed`；`partial` 至少有一个已知成员，`unknown` 不列确定成员，二者都须保留不确定性。未消解集合只能使用未知成员，不把候选身份冒充成员；其 `possibleEntityIds` 只能指向已提出的集合。其它未消解对象的候选也须属于相同 `referentKind`。

关联依据是模型或用户提出的判断，结构校验不证明它真实。身份依据继续通过原文提及、`basis`、`rationale` 和不确定性保留；计划与执行分开后，具体关系仍由知识陈述表达，不扩展通用图关系类型。

### 8.2 引用与接纳

新模型引用只包含 `evidenceRef`、连续原文 `quote` 及可选的零起始 `occurrence`。宿主枚举指定消息中全部精确匹配，包括重叠出现；唯一匹配时可省略序号，多处匹配时必须明确序号。缺序号、越界或原文不匹配分别拒绝；不信任模型字符偏移，不提供前后文旧入口，也不默认取第一处。

这降低构造长前后文的负担，不证明选对了语义位置。仍拒绝同一来源跨度重复绑定。集合只生成一条对应提及，个体陈述须引用成员自己的提及及支持陈述的来源；模型不能把集合位置复制给成员补数。案例行动／结果只能引用 `descriptive` 陈述，计划要求继续按其陈述性质表达。

无效关联会使包含它的实体不能接纳；依赖该实体的提及、集合、未消解候选或知识继续按闭合规则拒绝，保留逐项原因。关联和成员信息不能通过删除无效项悄悄变成“完整”。纠正必须原样提交或显式修改这些字段，不根据合并操作自动转移结果。

### 8.3 版本与存量影响

| 对象 | 替换前 → 当前 | 影响 |
|---|---|---|
| 实体历史 | `entity-analysis-history` v1 → v2 | 实体新增指代层次、组件关联及成员结构；旧实体历史拒读，目录计入不可读分析。 |
| 提炼运行 | `knowledge-extraction-run` v3 → v4 | 准备意图、原始模型输出和新提示词绑定；旧运行拒读，不能恢复。 |
| 提示词／模型输出 | `knowledge-extraction-v3`／输出 v3 → v4 | 新身份与引用语义，须使用新摘要；旧响应不进入新接纳器。 |
| 知识历史 | `knowledge-item-history` v2 → v2 | 正文和当前 grounding 结构不变；旧知识正文仍可读取，但绑定旧实体历史时显示实体分析不可用。 |

旧文件保持原样，不自动改写、删除、转换或迁移，不添加兼容 reader。用户使用新的空知识目录，从原始记录重新提炼；只有新版本运行能够按原幂等身份恢复。旧知识不会被重新生成的同名对象自动接管。旧质量报告、语料和证据不重算。

### 8.4 交付边界

本轮实现身份与关联校验、模型引用、提示词、宿主身份映射和写入／恢复边界，并让现有纠正入口完整传递新字段。可见的成员／组件操作与检索体验由 P3 补齐；P2 不将仅靠文本描述的关联展示说成已完成。

使用无模型调用的回归验证空结果、同名隔离、集合与未知、无效关联级联拒绝、重复引用、案例角色、幂等恢复及旧版本拒读。独立标注、真实数据和新模型调用仍按 P4／P5 另行完成；旧验收入口不得将新提示词与旧实体验收标准静默组合。
