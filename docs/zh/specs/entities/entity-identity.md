# 实体身份规则

本规范负责来源支持的身份规则与正反例。[实体提取规范](./entity-extraction.md)负责当前执行及存储契约；[评测协议](./entity-extraction-evaluation.md)单独维护质量版本、被测范围及就绪状态。[建设设计](../knowledge/knowledge-domain-model.md)连接窗口身份、跨窗口核对与知识维护。

本规范沿用[知识的概念定义](../../explanation/knowledge.md)：实体是知识描述的事物，知识表达它在特定上下文中的状态、关系或行为。规则由 OMK 自主实现，借鉴成熟设计，不要求引入第三方记忆框架、图数据库或额外模型。

对象含义、实体与陈述角色的概念统一见上述知识原理；本页集中规定来源支持的粒度、共指、消歧和引用规则。

## 1. 用户需要从实体找到什么

实体提取应帮助人和 AI 回答以下问题，而不是尽可能列出所有名词：

| 使用场景 | 应能得到的结果 | 身份错误的后果 |
|---|---|---|
| 查某组件的经验 | 找到测试和生产的不同表现，并读到各自的条件与证据。 | 误合并部署对象或丢失条件，把局部成功当作整体成功。 |
| 查具体部署的故障 | 明确是哪一个实例、何时发生、哪些修复仍未验证。 | 把另一个实例的成功或修复移用过来。 |
| 找改名后的文件 | 有改名依据时沿同一文件追溯旧名称与关联知识。 | 改名产生重复对象，或同路径的新文件继承旧文件知识。 |
| 区分计划与结果 | 分别找到计划要求、实际执行及已观测结果。 | 把“准备做”当作“已经做完”。 |
| 核对“它／它们” | 回到原文，看得到指代依据、集合成员或身份缺口。 | 任取一个对象，或把集合中的共同描述错误分配给个体。 |

当前身份边界仍是一份不可变来源窗口及其分析修订。工作区检索可以同时展示多个窗口的同名对象；它们不因此成为一个跨窗口身份。人工确认的[知识库组织](../knowledge/knowledge-library.md)引用这些身份，不替换它们。自动跨 Agent 消歧不在本规范范围内。

## 2. 判定流程与基本规则

按以下顺序判断每处值得保留的提及：

1. 保留来源原文与位置，先确认它谈的是事物、属性值还是一项陈述。数值、环境词、失败状态不必独立成为实体。
2. 判断原文所指的层次：组件、明确的版本对象、部署实例、文件、计划、执行活动或集合。只选择来源支持的粒度，不补造更具体的对象。
3. 只在有对应依据时复用窗口内的身份：明确的别名／改名、带来源命名空间的标识，或可解释的上下文共指。外部标识还需说明所属项目、系统及可见的有效范围；不能假定它永不复用。
4. 来源明确区分的对象必须分开。名称、类型、路径、字符串／向量相似度只能帮助找候选，不能单独证明同一身份。
5. 无法确定指向哪个对象时，保留一个未消解对象及理由；有明确候选时保留候选，不任取一个。身份已知而环境、版本或结果未知时，保留该身份，在陈述中说明未知条件。
6. 全窗口核对晚到的澄清和纠正，再绑定知识的主体／对象及上下文。新分析或纠正不得回写旧修订。

模型负责语义判断；程序负责原文定位、身份与引用闭合、修订绑定等确定性检查。结构通过不证明消歧正确；相同文本出现两次，也不证明两处提及属于同一对象。

### 2.1 事物、属性与过程的粒度

**先保留知识谈论的事物；属性、状态和行为默认由关于该事物的知识陈述表达。** 属性或过程也可以成为实体，但须由来源把它作为可独立指向、定义、比较或关联知识的对象讨论。不能仅因出现一个名词、复合词、数值或动词，就建立独立身份。

判断依据是来源中的讨论方式：是否给出了该对象自身的定义、区别、关系、规则或活动边界，是否把不同提及持续指向它。专名、编号、重复出现和已有知识候选都不是必需条件；普通概念也能成立。用户可能需要检索某个词，不足以补造来源未建立的对象；从知识陈述找到属性或行为，也不要求为它们各建实体。

| 来源表达 | 应保留的对象与知识 | 不应采用的处理 |
|---|---|---|
| “Session 是跨异步事件的归属概念。Session 计数只按初始化增加；Session 状态更新不新增计数。” | 保留 Session 概念；将计数规则和更新行为分别作为关于 Session 的陈述，保留肯否。此处不要求计数和状态更新各有独立身份。 | 只提取计数／更新而遗漏 Session；或强制按三个名词拆出三个实体。 |
| “会话总数指标 S_total 与活跃会话指标 S_active 不同。S_total 由初始化记录计算，告警规则 R 使用它。” | 来源独立定义并区分两个指标，保留指标与规则 R；由来源建立规则使用指标的关联。 | 把两个指标合成一个 Session 属性，丢失各自定义和规则归属。 |
| “状态更新是生命周期中的一种操作；它与初始化不同，可以重复发生。” | 来源将状态更新作为独立操作概念讨论，可保留该概念及初始化概念；关于它们的区别与行为仍用知识陈述表达。 | 以没有专名为由排除抽象概念；把一般操作概念记录成一次已发生的活动。 |
| “昨天的更新活动 U1 失败；今天计划执行 U2。” | U1、U2 是来源分别指向的活动；失败与计划状态分别表达。 | 合并两次活动，或把 U2 记为已执行。 |
| “这把键盘重 800 克，苹果售价 5 元。” | 保留键盘与来源语境中的苹果；重量、价格及数值是陈述，不因此成为独立对象。 | 为每个属性值建立实体，或凭价格猜测苹果的品牌／品种。 |
| “本轮只检查 Session 归属适配，尚未确认结果。” | 来源明确圈定检查对象，可保留 Session 归属适配及所谈 Session 概念；检查范围与未确认结果是陈述。 | 把检查对象的存在解释成适配成功，或机械把所有含 Session 的产品名称拆开。 |

这项规则决定对象是否需要独立身份，不取消原文、条件或知识陈述。没有知识候选时仍可保留来源支持的对象；来源不足以确定归属时保留不确定性，不能为了减少实体数而隐藏歧义。具体活动也不因尚未执行而失去身份，计划／已发生的区别由有来源的陈述表达。

这些规则不证明模型质量通过。新标注须在输出前冻结；已查看输出的窗口只作开发回归。修改规则不能回写原始输出、标注或分数。

### 2.2 配置点与关联知识的保留范围

**配置值通常是关于对象的知识，不因是字符串、布尔值或数值就独立成为实体。** 来源单独讨论某字段的用途、取值或适配合理性时，可保留字段对象；背景配置不要求逐项建实体或生成知识。值本身被独立定义、比较或持续讨论为状态概念时，再按 §2.1 判断是否需要身份。

选择提炼某配置点的知识时，若删掉一个值或限定会改变原文判断、让读者无法复用该设置，就必须在对应知识陈述中保留：

- 哪个对象或字段、精确取值，以及来源支持的拥有者／环境／版本范围；代码 literal 的大小写和类型不能擅自替换。
- 来源说明的用途、约束或理由，以及影响复用的条件、例外和未知；没有理由时不补造作用机制。
- 对应原文证据和来源说法的可信边界；“适配合理”的来源判断不表示已有工具验证或普遍成立。

字段作为主体时可写“配置值为 `unhandled`”，在 context 保留所属客户端和适用范围；没有单独字段身份时，也可用已有所属对象为主体，写清字段名称和取值。归属未知时不补实体。`description` 和 `qualifiers` 辅助识别，不能代替实质知识陈述；只查到字段名称或回到原文，不等于派生知识已经保留了配置事实。

以下为合成正反例，不是新的冻结标注答案：

| 来源表达 | 应保留的对象与知识 | 不应采用的处理 |
|---|---|---|
| “客户端 L 的 `errorStatus = 'unhandled'` 合理，因为该宿主的未处理异常不等于进程崩溃。” | 选择这项判断时，保留字段、精确值、所属客户端、宿主范围及来源理由；未见工具证据时仍是来源说法。 | 只写“配置合理”或只保留字段实体；凭字段名补造其它宿主的行为。 |
| “客户端 L 的 `errorStatus` 为 `'unhandled'`；客户端 M 的同名字段为 `'fatal'`。” | 字段与值分别对应所属对象；来源单独讨论字段身份时不可合并。 | 同名即合并，把一个客户端的值归给另一个。 |
| “同一服务的 `enabled` 在测试环境为布尔值 `false`，生产环境为字符串 `'false'`。” | 保留类型与环境；字段身份不因环境变化自动拆开。 | 将两个值都改写为“已禁用”，或推断原文未给出的运行效果。 |
| 背景配置罗列多个字段，本轮只谈部署失败，未要求完整配置摘要。 | 可只提炼相关部署知识；未选择的配置知识记为未观测。 | 为所有键和值建实体，或以实体完整推断配置知识完整。 |
| 输出前已冻结“必须覆盖 L 的配置值及理由”，结果只有字段实体，没有相关知识候选。 | 实体已提取，但必需知识覆盖未满足。 | 用结构允许空知识判为覆盖通过，或看完输出才新增必需项。 |

评价时分开三种情况：已生成相关知识却丢失关键值，是信息丢失；未选择可选配置知识，是未观测；未生成预先规定的必需事实，是知识覆盖缺口。它们不自动等于实体遗漏。必需事实、等价表达和范围须在输出前冻结，程序不通过字段关键词替模型补写事实。

配置知识是否完整与实体是否存在分别验收；上述合成例不作为模型质量通过的证据。

### 2.3 提及边界：完整名称与属性归属

**提及须指向所绑定的事物，边界不以字符越短越好。** 有助于独立指向同一对象的完整名称或限定描述可以保留；属性、结果或整条陈述不因包含对象名称而成为该对象的别名。

| 来源表达 | 可用提及边界 | 不应采用的处理 |
|---|---|---|
| “当前 main 的被测代码与已发布 r2 均通过。” | 当前代码状态可用“当前 main”或“当前 main 的被测代码”；是否同一身份仍按全文判断。 | 因完整描述比短名长而判错，或把整句作为版本名称。 |
| “服务 S 的 enabled 字段在测试环境为布尔值 false。” | 字段可用“enabled”或“enabled 字段”；值、类型与环境进入知识陈述。 | 机械去除所有“字段”后缀，或用整个赋值陈述作为字段名称。 |
| “main 上的改造还未发布。” | 代码状态的提及选“main”；改造及未发布另作关于该状态的知识。 | 把“main 上的改造”整个属性短语当作代码状态别名。 |
| “这把键盘的重量为 800 克。” | 键盘提及选“这把键盘”；重量和值属于该对象的陈述。 | 将整个重量短语绑定为键盘名称。 |

完整描述与属性归属按语义区分，不按“的”“上的”等词机械截断。属性本身满足 §2.1 的独立讨论条件时可有独立身份；限定词也可能是对象名称的必要组成。各处提及的原文定位、所属身份和知识陈述范围分别核对。收窄到重复短名后，须重新确定 occurrence；唯一长短语的序号不能直接沿用到短名。

**标识内部出现同样的字符，不等于该概念在这里被提及。** “_pendingTaskStatus；固定 Task；迟到事件不影响新 Task”中的概念提及是 occurrence=1 和 2；occurrence=0 属于字段内部。序号仍计入所有精确匹配，不跳过字段重新编号、不自动迁移到下一处。字段可使用完整标识；陈述引证可以包含字段。每条 `rationale` 解释实际选中的那一处，不能用最后一句的理由解释表格中另一处同名文字；需要两处时分别建提及。

新生成和新纠正使用 `mention_identifier_fragment` 拒绝切开连续 ASCII 字母／数字标识的提及，标识中间可含 `_`／`$`。单独的 Markdown 包裹符、中文相邻词和标点不因此拒绝；完整标识仍可接纳。此检查只覆盖词法片段，不判断中文分词、同名含义、理由正确性或所有编程语言的标识语法；位置 `matched` 仍只表示原文精确一致。旧修订不重验或回写，引用陈述的 citations 不使用此提及约束。

验收只精确匹配输出前声明的等价边界；更长且包含短名的引文只提供复核线索，程序不自动裁剪、补写或以关键词／正则决定含义。离线回放证明匹配与接纳行为，不证明模型选择已经改善。

### 2.4 Issue／PR 概念与具体工作记录

**来源独立讨论 Issue、PR 的概念或机制时可以建实体；具体编号的 Issue、PR 保留为来源侧工作记录，不单独建立实体身份。** 编号、链接、标题或状态不构成建实体的理由。相关标识、链接和状态保留在来源引用或案例 context 中，继续区分报告者和是否已经核验。

| 来源表达 | 应保留的对象与知识 | 不应采用的处理 |
|---|---|---|
| “Issue 用于跟踪问题，PR 用于提交改动并接受审查，两种机制职责不同。” | 来源独立讨论概念时保留 Issue、PR 实体，职责作为知识陈述。 | 因具体编号工作记录不在实体范围，就排除 Issue、PR 概念。 |
| “Issue #42 已创建，PR #73 已合入。” | 在来源证据或案例 context 中保留记录标识和所报告状态；存在有据主体时，将有用知识关联到该主体。 | 单独建立 Issue #42／PR #73 实体，或剥掉编号，补造来源没有独立讨论的 Issue／PR 概念。 |

这是针对这类工作记录的有限输出范围规则，不是排除具体对象或所有实例。来源支持的文件、部署、版本制品、计划与活动仍按各自身份规则处理。不能为了替代被排除的记录，就将其标题泛化为新概念；来源没有有据知识主体时不补造主体。

## 3. 组件、版本与部署实例

**组件身份默认表示来源持续讨论的系统或模块。环境、版本和时间通常限定陈述，不自动创建新实体。** 当来源明确讨论可分别指向的部署、实例或版本对象时，为它们建立独立身份；组件与实例的关系须有来源依据，不能靠同名推导。

来源中的架构职责可以支持组件层次，无需逐字写“持续系统／模块”：被持续覆写／升级的库，或通过继承、覆写方法承担客户端适配职责的类，都可有 `component` 依据。单个类名、函数名、一次调用或一次故障仍不足以证明层次。持续库与独立讨论的版本对象分别保留；组件名称在版本短语中独立指向该库时，短名称跨度与完整版本跨度可以重叠，但不能复制同一位置。`componentRef` 绑定已有组件和来源提及，不从版本名补造未讨论的库，也不为普通版本条件强制增加对象。

| 来源表达 | 应采用的身份与陈述 | 不应采用的处理 |
|---|---|---|
| “Harbor 使用 Quartz 调度器。测试环境中 Quartz 通过；生产环境中 Quartz 报错，修复未验证。” | 一个 Quartz 组件；测试通过、生产报错、生产修复未验证分别保留条件。 | 仅因环境不同强制拆出实例，或省略生产条件，写成“Quartz 已通过”。 |
| “Quartz 的测试实例 T 通过；生产实例 P 报错。它们部署在不同环境。” | T、P 是两个实例；有组件提及时保留 Quartz 组件，来源支持二者属于该组件。 | 把 T、P 合并，或以抽象组件替代明确的实例指代。 |
| “T 已升级到 v2，仍是昨天那个实例。” | T 身份延续；升级前后版本和状态属于不同时间、条件下的陈述。 | 每次升级都为 T 重新分配身份，丢失连续历史。 |
| “对比 Quartz v1 与 v2 的发布包；这两个包分别归档。” | 两个明确的版本对象；组件身份与包身份分开，包的版本固定。 | 把两个不可变发布包合并；或将一次比较推广成所有版本都必须是实体。 |
| “Quartz 通过了，但记录没说在哪个环境。” | 已知所谈组件时保留 Quartz；环境未知，成功范围有限。 | 为未知环境制造“未知 Quartz 实例”，或把成功应用到生产。 |
| “T 和 P 都叫 Quartz。它报错了，暂时不知道是哪一个。” | T、P 分开；“它”属于一个未消解实例，候选为 T、P。 | 选择最近出现的 P，或把实例歧义隐藏到抽象组件上。 |

**冻结归档的制品同样是版本对象，不限于代码状态。** 来源冻结、归档或以版本标识与摘要登记的数据集、语料、schema 或构建，以 `version` 身份识别，版本号可以出现在名称中；它所属的持续规范、提示词或工具保持 `object`／`component`，当前版本只进限定或陈述。不因为制品不是代码就把它标成普通 `object`，也不因为提到当前版本就把持续事物拆出版本身份。

| 来源表达 | 应有的身份与陈述 | 不允许的处理 |
|---|---|---|
| 「回归语料已冻结为 omk-entity-quality/v12，摘要已登记，此后只读。提取提示词继续迭代，当前是 v14。」 | 冻结的 v12 语料用 `version`；提取提示词作为一个持续 `object`，v14 只作限定。 | 把归档语料标成 `object`，或为持续提示词另建版本实体。 |

“生产 Quartz”这一短语本身不足以决定粒度：上下文在描述组件的生产表现时沿用组件；已建立生产部署指代时引用那个实例。两者无法区分且会影响知识归属时，显式保留粒度不确定性，不能悄悄改成更抽象或更具体的对象。

**组件与实例不是可随意互换的主语。** “实例 P 失败”可以帮助用户从组件找到相关经验，但不能自动成为“组件所有实例都失败”。检索到相关对象的知识与将主张推广到相关对象，是不同动作。

组件／实例和组件／版本的关联使用 §8 的版本化字段；当前 Studio 支持显式纠正，目录检索保留来源与分析修订绑定，具体行为见[实体提取规范](./entity-extraction.md)。

### 3.1 分支名称与被测代码状态

**`master`／`main` 等名称不决定指代层次，来源谈论的对象才决定。** 分支本身是持续移动的代码指针，按 `object` 保留；来源单独比较、测试或归档的某次代码状态可以是 `version`，不要求一定有 commit SHA 或正式版本号。来源须支持可分别指向的状态；缺少复现标识时保留未知，不补造 SHA、发布号或发布事实。

| 来源表达 | 应采用的身份与陈述 | 不应采用的处理 |
|---|---|---|
| “修复合入 master，后续开发继续在这个分支上进行。” | master 分支对象，持续身份；合入事实另作陈述。 | 把移动分支当作固定提交或发布包。 |
| “对比 master 的提交 a1 与 a2，各自运行同一测试。” | 两个分别指向的版本状态；来源也讨论分支时可保留分支身份。 | 因分支同名合并两个被测版本。 |
| “当前 master 的被测代码与已发布 beta.2 均通过；master 上的改造尚未发布，未记录提交号。” | 被测状态可用 `version`，提交号未知且尚未发布；采用分支 `object` 时，陈述须限定本次被测状态和来源时间。 | 仅因名称是 master 排除版本解释；补 SHA、视为已发布，或推广为未来所有 master 都通过。 |
| “昨天与今天的 master 构建不同，分别比较结果。” | 一个持续分支及来源明确区分的两次代码状态；仅保留来源实际提及的身份。 | 合并明确不同的被测状态，或仅凭日期拆出两个分支。 |
| “master 通过了”，窗口未说明在谈分支还是某次构建。 | 已知对象保留对象和粒度／测试范围未知；只有指向本身未知才用未消解身份。 | 仅因没有 SHA 宣称身份未消解，或补造具体部署／版本。 |

分支和代码状态不能互相替代，也不能把同一原文位置复制成两条提及。`componentRef` 仍需来源中的持续组件及关联依据，不能由分支名补造组件。版本身份不意味着已具备可复现构建证据；分支身份也不能把一次结果提升为持续属性。

冻结标注可在来源支持两种建模时列出允许的 `object`／`version`，仍须逐例核对状态限定和知识归属，不按名称一律放宽。允许表达须在输出前确定，不能用新裁决提高旧分数。

### 3.2 发布包与本次被测构建

**同一名称或话题不证明同一产物，身份限定不能跨对象继承。** 先讨论已发布包、后讨论真实构建的测试，不足以确认被测构建就是该发布包；版本串相同、测试晚于发布，也不是对应依据。只保留来源支持的发布状态、版本、环境与测试范围。

| 来源表达 | 应保留的身份与陈述 | 不应接受的处理 |
|---|---|---|
| “已发布 beta 仍待后台验收；这次用真实 beta 构建做了对照。” | 本次被测构建可以是已知的 `version`；发布状态、精确构建及是否为前述包未知。如两者都独立识别，先分开保存，不宣称已确认不同。 | 把被测构建写成已发布 beta，或把对照结果归给发布包。 |
| “R 是已发布包，T 是本地构建；二者不是同一产物。” | 两个来源明确区分的对象及各自限定，结果分别绑定。 | 因名称或版本串相同而合并。 |
| “测试的就是前述发布包 R，同一产物。” | 按明确对应归并提及，理由保留来源依据；测试结论仍限定本次条件。 | 每次测试强制另建版本，或将一次结果推广到所有环境。 |

不确定的是发布状态或产物对应关系时，已知被测对象仍可为 `proposed`，不因缺 SHA 改为 `unresolved`。未知信息进入实体 `uncertainties` 和受影响陈述的 `context.unknowns`；`description`／`qualifiers` 不得补造限定。陈述中的“版本未知”不能抵消主体实体被无据限定为已发布；须同时复核实体与知识引用。

当前提取提示词落实本节规则。结构接纳只检查引用与位置，不能判断构建同一性；不使用 beta 关键词自动拆分、合并或改写结果。已有输出的显式纠正只验证表示、保存和知识修订，不证明模型自动提取改善。提示词及响应版本由[提取规范](./entity-extraction.md)维护。

### 3.1 规范接口、实现与入口

**实现某接口、兼容其行为或提供替代入口，不证明与接口或其它实现是同一对象。** 来源分别独立讨论规范接口与具体实现时分别保留；只有来源给出同一实现的别名或入口对应时，才据此绑定相应提及。不为每个名称机械拆出接口、实现、入口三层，也不凭常识补规范名称、作者或自写归属。

例如，来源明确“RouteLedger 定义读取契约，模块 PebbleLedger 实现该契约；./ledger-entry 只是 PebbleLedger 的另一个导入入口”，可以分别保留接口与实现，路径提及按明确对应绑定实现，不另造一份实现。来源只分别比较 ClayReader 与 ./route-reader、未说明对应关系或入口作者时，不能把路径绑定到前者或描述成自写实现；也不从路径补出未被独立讨论的接口。

逐处判断实际所指，不用标准接口替代明确的实现，也不将实现名称的出现自动算作接口概念。身份已知而作者、类型或对应关系未知时，保留对象和具体未知；某处确实无法确定指向哪个对象时，保留局部 `unresolved` 与有据候选。类型与候选继续遵循既有来源和同层次约束，`componentRef` 不表达“实现某接口”。这些判断由模型和语义复核负责，程序不按 API 名、路径或“自写”等词语分类或自动修补。

## 4. 集合、未知身份与提及位置

**集合是一个共同指代的对象；未知身份是不知道指向哪个对象。** 两者不能用一个笼统的“未知”标签替代。

| 来源表达 | 应保留的结果 | 不应采用的处理 |
|---|---|---|
| “Aster 和 Birch 是两个服务。它们都启动了。” | Aster、Birch 分开；“它们”是一处集合提及，成员为二者；“都”支持分别陈述二者启动。 | 将同一个“它们”位置复制成两个个体提及。 |
| “Aster 和 Birch 协同完成任务，耗时十秒。” | 共同参与的集合／活动及整体结果；来源未给出每个服务的耗时。 | 给每个服务各写“完成任务耗时十秒”。 |
| “Atlas 和 Beacon 之一报错了，它尚未修复。” | 一个未消解对象；可能身份为 Atlas 或 Beacon。 | 建立确定的 Atlas＋Beacon 集合，把二者都标成报错。 |
| 截断窗口只剩“它们还未确认。” | 保留未消解的复数指代、成员未知及窗口限制。 | 虚构成员，或当作已知单个实体。 |

已知集合可以保留部分已知成员与成员缺口；不能把不完整成员表当作全集。候选必须属于相同指代层次：“它们”可能指不同组合时，不能将单个 A、B 填成两个可任选的单体候选。候选组合无法有据表达时，保留文字说明与未知，不编造没有提及依据的集合身份。

**集合主体是否明确与成员是否完整分别判断。** 来源独立指向一组对象，知道是哪一组但未列成员时，可保留 `proposed` 集合、`completeness=unknown`、空 `memberEntityIds` 及成员缺口理由；不因成员未知改成 `object` 或删除集合，也不按数量补占位成员。来源只给部分成员时使用 `partial`，只列有据成员；连所指的组都无法确定时才是未消解集合。

例如，“本次封存的七张岩样卡作为一组核验，单卡编号未记录”支持身份明确、成员未知的集合；“岩样卡是一类记录载体，本次只讨论其定义”讨论抽象类别，可为 `object`；“《砂纹册》是一份登记册，本次核对它的封面说明”讨论单一制品，也可为 `object`。类别可有多个实例、制品包含多页，都不自动构成集合；复数、数量词或类型词不替代来源中的共同范围依据。

每处接纳的原文位置只对应一条提及。集合提及、成员关系和由“都”支持的个体陈述分别表达，不能靠重复位置完成分发。当前重复位置拒绝规则保持；§8 定义集合成员、复数歧义和个体陈述的证据绑定；结构测试不证明模型提取质量。

引用使用原文连续短语；重复文本须明确零起始出现序号，重叠匹配也计数，唯一匹配可省略。宿主拒绝歧义位置，不模糊匹配或任选第一处。UTF-16 位置仍由宿主计算；§8 替换旧的前后文引用方式。

## 5. 改名、复制、计划与执行

| 来源表达 | 身份规则 | 需要保留的边界 |
|---|---|---|
| “项目 A 的 a.md 改名为 b.md，仍是同一文件。” | 延续文件身份，保留有依据的旧名／新名和时间。 | 不改写旧修订里的名称或位置；不推断功能变化。 |
| “项目 B 也有 b.md。” | 与项目 A 的文件分开。 | 同路径、同内容或同类型不构成跨项目身份依据。 |
| “删除旧 b.md 后，在原路径新建了另一个文件。” | 旧文件与新文件分开，即使路径相同。 | 路径是定位信息，不是永久身份。 |
| “把 a.md 复制为 b.md，两个文件均保留。” | 两个文件身份；复制关系有来源支持。 | 不能把复制当改名或把相同内容当同一文件。 |
| “BuildKit 写出 build.log；它下次还会覆盖这份日志。” | 工具与日志分开；按上下文确认“它”指工具。 | 不把日志中的工具名、命令或攻击文本自动当作当前操作。 |
| “R1 是发布计划；D1 是按 R1 进行的测试演练，生产发布尚未开始。” | 计划 R1、执行活动 D1 分开；可有来源支持的执行依据关联。 | 测试演练成功不证明生产发布完成，也不证明计划有效。 |
| “明天再按 R1 演练一次 D2。” | R1 仍是计划，D2 是另一项计划中的执行活动。 | 把 D2 与 D1 合并，或把未来活动记录成已经发生。 |

时间和版本变化本身不决定新身份。有明确连续性时保留身份与不同时段的状态；有替换、复制或另一次执行的依据时分开；连续性证据不足时保留不确定性。计划、规则和概念可作为实体，但其中的要求、适用范围、行为与结果仍需作为有证据的知识陈述。

## 6. 晚到纠正、存储与展示要求

来源说“刚才说错了，报错的是生产 Quartz，不是 Cedar”时，分析应按明确纠正重新判断相关指代，保留前一说法及纠正依据。纠正某个对象的名称／归属，不会证明其报错、修复或成功结果是真的。不同说话者的相互矛盾也不等于后一条自动胜出；无法裁决时保留冲突与来源。

**未确认的身份候选与明确撤回的猜测不同。** `possibleEntityIds` 表示有据的可能对应，未确认不等于已排除；名称相同、共同出现或助手选择回答某对象也不自动建立对应。逐项核对全窗口中的候选依据与撤回范围：唯一对应依据明确撤回且无剩余支持时，原含糊对象保留 `unresolved` 和缺口理由，不继续保留失去依据的候选关联。被猜测的对象若本身仍符合实体范围，可保留其明确名称提及及猜测语境，不因此恢复该关联。

例如，“灯桥”最初所指未知，仅凭同名猜为“灯桥检索器”，随后明确撤回该猜测且无其它依据时，原指代使用空候选及撤回理由。来源明确只可能为“灯桥检索器或灯桥索引器”、后来只是说尚未确定时，保留两个有据候选；若后续只撤回选中其中一个的猜测，独立的二选一范围仍然成立，不清空全部候选。不同说话者分别主张这两个对应但无可裁决依据时，保留冲突与未决，不按时间或角色自动决定。程序校验候选引用与层次，不能确定来源是否支持或撤回了语义对应。

当前存储和展示要求：

- 分开显示对象标签、指代层次、身份依据、限定信息、成员／相关对象及未知项；不能用一段描述承担全部信息。
- 名称是检索入口；分析／实体／修订身份才是当前窗口绑定。同名对象在目录里分开展示，使用来源和限定帮助区分。
- 组件与实例、集合与成员的关联只表示原文支持的关系；不自动合并知识、转移结果或计算因果收益。
- 新分析保留父修订、理由与原始证据；现有知识继续绑定生成时的明确修订。把纠正用于知识须创建新知识修订，用户仍可查看旧绑定。
- 拆分后不能任选一个新对象继承旧知识主语。来源不可用、成员不完整或关联知识读取失败，应分别展示限制，而不是“没有对象／没有知识”。

这些要求补充[修订与存储边界](./entity-extraction.md)。§8 明确已批准的版本替换及存量影响，不添加兼容 reader、自动迁移或持久索引。

## 7. 从规则进入实现与验收

本页正反例用于规定规则，不是独立裁决的 gold，也不是提取能力已经改善的证据。标注、回归和独立复核闸门及当前证据由[评测协议](./entity-extraction-evaluation.md)维护。

集合主体与对应依据的澄清先由独立研究候选验证，不因此切换生产默认或改变 wire、Schema、接纳与存储契约。候选须冻结实际 prompt 字节并用真实对话受控比较；规则和合成回归通过不表示模型已经遵守，也不重写旧候选或历史研究结论。

验收不能只比较实体数量：需检查对象层次、必要的身份分离、共指依据、集合／未知表达、知识主体／对象与条件，以及纠正后的修订绑定。关键提及和应有身份须在输出前标注；不能只检查模型返回的对象，也不能让模型省略实例以规避误合并。

允许同义标签和有来源支持的额外对象，不允许用抽象组件替代明确实例、将集体结果分配给个体，或丢失影响复用的条件。组件粒度的跨环境陈述可以合格，前提是来源没有建立必须分开的实例且条件完整；独立复核须按这些规则判定，而不是按返回 ID 数量判定。

新身份规则、标注与检查程序须使用新的测量身份，才能报告后续质量；不回头改 gold 或重算旧结果。

## 8. 当前身份契约

当前身份、关联与引用契约已落实到提示词、接纳、宿主身份映射、存储恢复、纠正及检索展示。结构与使用动线通过不替代独立质量验收。

### 8.1 最小身份结构

现有实体包含三个必填字段，不建立第二份全局对象库：

| 字段 | 语义与校验 |
|---|---|
| `referentKind` | `object`、`component`、`instance`、`version`、`collection`、`plan`、`activity`；普通人、文件、工具、规则和概念可用 `object`。这是指代层次，不是可信度。 |
| `componentRef` | `null`，或包含 `entityId`、`mentionIds`、`rationale` 的关联。只允许实例／版本关联一个已提出的组件；目标和提及须属于本分析，至少一处提及属于该实例／版本。未建立组件身份时为 `null`，不按名字补造。 |
| `collection` | 非集合为 `null`；集合包含 `memberEntityIds`、`completeness`、`mentionIds`、`rationale`。完整性为 `complete`、`partial` 或 `unknown`；提及中至少一处属于该集合。成员引用不重复、不悬空、不形成直接或间接自包含。 |

集合成员完整性与身份消歧分开：已知集合可以有成员缺口，仍为 `proposed`；`partial` 至少有一个已知成员，`unknown` 不列确定成员，二者都须保留不确定性。未消解集合只能使用未知成员，不把候选身份冒充成员；其 `possibleEntityIds` 只能指向已提出的集合。其它未消解对象的候选也须属于相同 `referentKind`。

关联依据是模型或用户提出的判断，结构校验不证明它真实。身份依据继续通过原文提及、`basis`、`rationale` 和不确定性保留；计划与执行分开后，具体关系仍由知识陈述表达，不扩展通用图关系类型。

### 8.2 引用与接纳

新模型引用只包含 `evidenceRef`、连续原文 `quote` 及可选的零起始 `occurrence`。宿主枚举指定消息中全部精确匹配，包括重叠出现；唯一匹配时可省略序号，多处匹配时必须明确序号。缺序号、越界或原文不匹配分别拒绝；不信任模型字符偏移，不提供前后文旧入口，也不默认取第一处。

这降低构造长前后文的负担，不证明选对了语义位置。仍拒绝同一来源跨度重复绑定。集合只生成一条对应提及，个体陈述须引用成员自己的提及及支持陈述的来源；模型不能把集合位置复制给成员补数。案例行动／结果只能引用 `descriptive` 陈述，计划要求继续按其陈述性质表达。

无效关联会使包含它的实体不能接纳；依赖该实体的提及、集合、未消解候选或知识继续按闭合规则拒绝，保留逐项原因。关联和成员信息不能通过删除无效项悄悄变成“完整”。纠正必须原样提交或显式修改这些字段，不根据合并操作自动转移结果。

### 8.3 版本与存量影响

[提取规范](./entity-extraction.md)维护当前 prompt、wire／领域响应、run 及实体／知识历史版本、冻结 prompt 身份、不支持版本的行为及存量影响。[知识库](../knowledge/knowledge-library.md)与[实体关联日志](./entity-links.md)维护各自独立的组织及核对格式。提示词版本不是存储或测量版本，改变冻结请求须使用新 run 身份，不继承旧实验的执行许可。

旧文件、输出及证据保持原样，不自动改写、删除、转换、迁移，不添加兼容 reader 或重评分。不支持的实体历史明确不可读，可用知识保留原绑定及限制。同名新实体不继承旧知识；纠正须创建不可变新修订，只有支持的 run 格式才能按原幂等身份恢复。

### 8.4 交付边界

当前实现覆盖身份与关联校验、模型引用、提示词、宿主身份映射、写入恢复、纠正以及成员／组件展示与检索。具体交互与失败边界由[实体提取规范](./entity-extraction.md)规定。

功能回归覆盖空结果、同名隔离、集合与未知、无效关联级联拒绝、重复引用、案例角色、幂等恢复及旧版本拒读。质量证据及限制由评测协议维护；验收入口不得将现行提示词与不同测量身份的旧标准静默组合。
