# Knowledge maintenance, automatic extraction, and carrier contracts

This page owns implemented tags, explicit extraction and retired scheduling, carrier saving/rebuilding, change reminders, and evaluation association. Start with the [knowledge maintenance workflow](../../guides/knowledge/extract-knowledge.md); use this specification for fields, storage, and failure boundaries. The domain model and library specifications separately own content and organization links.

## Conversation auto extraction and project inbox

Current `knowledge-body-first/v4` permits explicit stages only: source ledger → body → source coverage → actual operator decision → association. Preview and confirm each complete model request independently. Source-coverage opinions are not content approval and never retain a body or update a carrier automatically.

Conversation scheduling is retired. Status returns `unsupported`/`explicit_stages_required`; preview, enable and background tick create no model, configure no executor, dispatch nothing and write no permission. Stop/close do not alter old permissions, reservations, unknown claims or originals; migration archives them. A migrated workspace cannot receive a renewed automatic grant: use explicit stages.

The conversation/project **Knowledge inbox** still groups body IDs by selected source conversation without assigning shared entity identity. It supports retain/discard/revise and independent association review. Explicit extraction completion or scoped maintenance events refresh it, without retired automation polling. Storage and recovery details are in the [workspace contract](../shared/storage-layout-spec.md#explicit-knowledge-workspace).

## Organize and find knowledge


Edit **Topic tags** in candidate details and explicitly save them. Use Chinese characters, letters, numbers, underscores, hyphens, or `/` for nesting, without spaces or purely numeric names. Each knowledge item allows up to 32 tags of 80 characters each. Duplicate tags are case-insensitive. Tags are user-maintained, make no additional model call, and do not verify knowledge. Editing tags leaves claims, sources, revisions, and retention decisions unchanged.

The library searches titles and tags. `tag:debugging` matches “debugging” and nested tags such as “debugging/evidence”, together with the decision filter. Tags organize topics; knowledge types, applicability conditions, and evidence classifications still come from the selected knowledge revision.

Tag history is stored separately in `tags/<identity-digest>.json` under the knowledge directory, using `omk-knowledge-tags/v1`. Records bind the knowledge identity and preserve tags, modification time, and actor. Saving tags does not change knowledge, source, or run records. Unset tags are empty; concurrent updates reject stale generations and require reloading and review. Tags persist across knowledge revisions as organization information; check that they still apply.


## Generate and save knowledge artifacts


Choose **Generate knowledge artifact** on a retained candidate or completed batch, or **Generate from retained knowledge** in **Knowledge artifacts**. Choose skill or prompt, enter a name, inspect the selected retained knowledge, and choose **Generate and review**. Initial selections include only the current candidate or retained items from this batch; explicitly add other retained items if needed, up to 100 per operation. Generation incorporates complete canonical segments with their conditions, attribution, negation, exceptions, unknowns, inline evidence bases, quotes and source versions. Derived association changes never rewrite carrier body text. It makes no additional model call.

Generation also exports a property snapshot: summary, topic tags, optional knowledge types, evidence bases, exact knowledge revisions/body digests and source versions. The summary uses knowledge titles; necessary scenarios remain in complete body text, not inferred typed contexts. Multiple evidence bases can coexist. `verification_status: not_assessed` means this generation provides no truth or task-effect validation. Prompts use top-level YAML properties with `tags` as a list, readable by tools such as [Obsidian](https://obsidian.md/help/properties). Skills retain required `name`/`description` fields and put additional properties in the specification's `metadata` string mapping; lists are encoded as JSON strings.

Properties use `omk-knowledge-metadata/v2` and describe knowledge incorporated in this artifact version; editing them does not update the knowledge library. Updating an OMK-generated artifact recomputes these properties. The first import of a local prompt preserves custom fields and existing tags. Tag changes after preview also reject stale saves. Older artifacts are not rewritten in the background; `manifest.json` remains authoritative for artifact and knowledge revision associations.

Review and edit the new content, then choose **Save artifact**. Content is saved directly under the current knowledge directory as `artifacts/<artifact-id>/vN/content/<directory-name>/SKILL.md` or `artifacts/<artifact-id>/vN/content/<directory-name>.md`. The artifact detail opens with the actual artifact path, content, knowledge sources, and version history. Display names may contain Chinese text. New artifacts receive distinct file names; skill frontmatter names match their directory names, and valid frontmatter is checked on save, following the [Agent Skills format](https://agentskills.io/specification). No clipboard step is required. Source links open the exact incorporated knowledge revision. Saving does not verify truth or effectiveness; check applicability and run a controlled evaluation before use.

To update an artifact, select a saved artifact or explicitly provide a local file path. Saved artifacts rebuild their knowledge region from the explicitly selected current retained revisions. Omitted knowledge is removed from the new version; content, properties and manifest reference only the selection. Manual content outside the region and assets are preserved. New regions use `omk:knowledge:v1` boundary markers. Unmarked old versions migrate only when the knowledge suffix exactly matches the manifest revisions; otherwise rebuilding is refused and a new artifact with reviewed manual content is required. Compare original content before saving a new version; old versions remain intact. Starting from local `SKILL.md` preserves original content and copies distributable assets in the same directory using existing filtering and content digest rules, without overwriting the original file. Choose another knowledge directory if the save location is inside the local skill being copied. Select the latest version before generating further updates.

**Knowledge review** in the artifact list and **Review changes** in details check existing references at read time: new revisions, current revisions not retained, and unavailable knowledge or sources prompt review. External file edits are indicated separately. Details show the check time, changed fields, and exact incorporated and current revision content. Choose **Recheck knowledge changes** to refresh; failed reads are not evidence of no changes. Checks exclude unreferenced new knowledge, do not assess truth or semantic expiry, and never automatically update artifacts or maintenance decisions. When generating a new version, **Reference changes in this update** lists added, replaced, removed and kept revisions. Compare the original content before saving; the latest version’s notices reflect a new read, while historical versions are still checked against their own references.

Each `manifest.json` uses `omk-carrier-v1`, recording artifact identity, version, save time, content digest, file directory name, baseline, and exact knowledge revision references. The carrier manifest identity remains separate from body Schema 3 and metadata v2; existing versions are not automatically rewritten. Knowledge review is a read-time projection and is not written to historical manifests. Changes to the current knowledge revision, retain decision, or artifact baseline after preview reject stale saves and require a new preview. External artifact edits are marked as content changes. A complete staged version is published atomically; failure or cancellation does not replace old versions. After a local writer exits, the next save recovers its dead lock once it is over 30 seconds old and removes unpublished staging; locks owned by another host are not taken over. If the save result cannot be read, choose **Check saved version** before attempting another write.


## Evaluate an artifact change


Select “Evaluate this version” in artifact details. Updates preselect the original version; new artifacts require another saved version or an explicit local skill directory/SKILL.md or prompt file as control. Both versions must have the same form and different content. Select a local sample file or directory, executor and fixed model, configure model judges if needed, then preview the evaluation plan. This entry supports 1–100 local samples and excludes samples requiring remote content resolution.

Preview shows both versions, identical samples and scoring criteria, the task model, actual scoring models and planned task count, without calling models. Only “Confirm and evaluate” starts execution, including required preflight. Cost cannot be estimated precisely; preflight and model grading may add calls. There are no automatic retries. Previews expire after 15 minutes; changed artifacts, samples or runtime plans require a new review.

Evaluation attempts bind the exact artifact revision and source knowledge. Finished, failed, cancelled and interrupted states remain visible for supported v2 records; cancel active work, open the Core results and evidence, then return to the evaluated version. Cancellation cannot undo calls or charges already incurred. If the start response is lost, check run status before another attempt. Server shutdown cancels owned work; attempts whose local process has exited show interruption and never restart model calls automatically. Existing Core results and evidence remain subject to their own supported formats.

The selected knowledge directory is the operation root. Core artifacts use the existing `.omk/eval` contract; `.omk/state/jobs/carrier-measurements/<measurement-id>.json` records use `omk-carrier-measurement-v2` for previews and attempt associations, without changing artifact manifests or Core measurement schemas. The current reader does not read or resume earlier v1 sidecars; keep their originals as history and preview a new plan against explicitly selected current sources and artifacts. Records may contain private samples and artifact content; manage them as local data. A finished run, saved artifact or retained knowledge does not establish effectiveness. Review report conclusions and evidence scope; generated samples require review and are not automatically independent release evidence.
