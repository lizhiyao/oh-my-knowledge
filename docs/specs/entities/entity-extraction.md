# Entity extraction from selected records

This specification owns window extraction, deterministic host admission, source/entity/knowledge bindings, current storage and invocation recovery. The [end-to-end construction design](../knowledge/knowledge-domain-model.md) connects extraction to cross-window organization, maintenance and carrier evaluation. Quality versions, measured scope and readiness belong to the [evaluation protocol](./entity-extraction-evaluation.md).

See the [identity rules](./entity-identity.md) for components/instances, collections/unresolved identities, renames/versions and later corrections. Section 6 defines current contracts; only current data structures are supported, without a legacy production reader; explicit new-workspace migration is separate. Human-confirmed cross-window organization is provided by the [entity-link journal](./entity-links.md) and [library](../knowledge/knowledge-library.md), without replacing window identities. Automatic cross-Agent identity merging is outside scope. Research, structural validation and functional completion do not establish model performance or reuse benefits.

## 1. User outcome and scope

The primary result is reusable, complete natural-language knowledge saved pending from one selected source window. Entity and optional typed association is a second independent projection, not the prerequisite or canonical body. See [knowledge principles](../../explanation/knowledge.md).

Generation inventories complete sources, saves admitted bodies, then independently compares sources, the fallible ledger and bodies. Association needs an exact actual Agent/human coverage decision and separate request confirmation. Zero bodies still need coverage. Missing or failed associations never block body reading, maintenance or revision; recognizing objects does not establish source faithfulness or task benefits.

Window entity meanings, mentions, qualifiers, referent levels and uncertainty remain inspectable. Names, paths, types and similarity do not establish identical objects. No automatic cross-window merging, embedding search or global graph is introduced. Cross-window library organization still requires the existing explicit human confirmation.

## 3. Contracts and identity

Current default `knowledge-body-first/v4` has source_ledger, body, source_coverage and association stages. Model analyses and actual decisions remain separate; see the [source review contract](../knowledge/knowledge-source-review.md) for scope/gates and the [generated contract](../../reference/shared/knowledge-contract.md) for identities/capacities.

The ledger uses wire2/prompt3 and coverage uses wire2/prompt3, with both histories remaining store1; body wire2 uses prompt9. Association now uses prompt8: only its prompt/profile/request identities change (**BREAKING-COMPARABILITY**), while wire3, the v1 stage envelope and existing data formats remain unchanged, without data migration. The earlier journal4/default input2 replacement of workflow3 was **BREAKING-SCHEMA/API/COMPARABILITY**; Source3/body3/entity2/association2/reviews1 stayed unchanged. Old originals, scores and occurrence-based historical protocols remain frozen; use [independent-copy migration](../knowledge/knowledge-sources.md#migration) for that earlier transition, never retroactive quality claims.

The body prompt determines a concrete case's scope before composing independently readable segments, including a case split into another proposal. A supported upgrade-background version is distinct from an unknown version implicated in a reported problem; general methods do not inherit unrelated case restrictions. The association prompt selects object mentions before mapping and checks each identified object across related same-source paragraphs about its definition, attributes, conditions, maintenance or storage. Valid own mentions may be reused without repeating a name or objectId in each paragraph; unrelated paragraphs remain unmapped. One declaration position cannot supply separate general-object/version mentions: Git metadata may qualify the object, while a separate version object needs its own source-supported mention. Independently referenced artifact/code states and necessary component/version mappings remain distinct. A property or problem statement is not a mention of its owning object, and a component link does not propagate retrieval mappings. These are model instructions, not deterministic semantic guarantees; raw quality still requires source review and actual scoped retrieval.

- Canonical body draft: `{title, content:{segments:[{segmentId,text,evidence}],organization?},reuseRationale}`. Each segment is complete and preserves necessary conditions, attribution, negation, time, exceptions, participant stances and unknowns. Titles, reuse hints, quotes and future catalogs cannot supply missing body content.
- Inline evidence: `{source:{snapshotId,sourceVersion},selection:{evidenceRef,start,end,quote},basis,interpretation?}`. Basis distinguishes source assertion, direct observation and inference; exact matching is not truth.
- Model locators use `{evidenceRef,quote,contextBefore,contextAfter}`. The quote and nullable contexts are literal adjacent text in one excerpt. The host requires a unique continuous `contextBefore + quote + contextAfter` match and computes the quote's UTF-16 positions without normalization or fuzzy matching; a mismatch or ambiguity is rejected. Models provide neither occurrences nor offsets. Structural/domain/reference checking preserves complete native originals.
- Each body proposal declares `requiredContexts:[{literal,evidence}]` for source-backed context shared by all its segments. A literal must occur verbatim in its evidence quote and every segment's text. The host appends that evidence to each segment, deduplicating complete evidence values without rewriting text. Empty declarations are allowed. Declared contexts do not prove that all necessary context or reusable content was identified. Compiled accepted drafts total at most 16 MiB of UTF-8 JSON; a proposal exceeding that capacity or merged evidence limits is rejected whole, without truncation.
- Derived associations bind `{knowledgeId,revisionId,bodyDigest}`, exact catalog revisions, `segmentEntityRefs`, optional `typedRelations`, and issues. Typed relations retain source roles/modality/polarity where projected but do not require all body meaning to become triples. Failure/rebuilding never revises body.
- Window entities retain source-supported `description`, `qualifiers`, `referentKind`, `identityStatus`, uncertainties and closed component/collection/candidate references. Every admitted entity needs a valid mention; identifier fragments, missing refs and invalid mention ownership fail admission. No deterministic check proves semantic identity.
- In association output, each entity owns `mentions` with entity-local `mentionKey` values. The host assigns persistent IDs and compiles catalog/entity/key-qualified references; equal keys under different entities are distinct. Component/collection links may cite only the declaring entity's own mentions and remain subject to existing referent-kind and reference-closure checks. Every body segment has exactly one `segmentDecisions` entry: `mapped` has nonempty entity references, `abstained` has none, and both require a reason. These AI decisions are diagnostics, not content or coverage reviews; abstention does not prove no relevant object exists.
- New body and derived revisions are pending. Body retain/discard and derived accept/reject are independent decisions; a new revision inherits neither decision.

### 3.1 Critical sources and ordinary repeated mentions

Each complete body segment directly cites locations supporting its important conditions, corrections, exceptions and unknowns. When attribution depends on earlier source context, retain that anchor alongside the claim evidence. Metadata-derived scope remains identified as metadata: never fabricate a quote from it or treat source time as fact time. Full-message access, a catalog description or rationale is not direct evidence for a body claim. A body segment must preserve the content itself, not just its quote.

For statements about changing implementations, production defaults, versions or completion status, the generation prompt requires every affected segment to retain the reporting date and speaker attribution from the supporting trace excerpt's `coordinate.timestamp`. The text identifies the date as message metadata and preserves its UTC or timezone basis; it is neither fact time, effective time nor verification in the current task. Evidence still quotes the actual statement verbatim, with `interpretation` identifying the same excerpt's `coordinate.timestamp` and its original value. Metadata dates never become fabricated quotes or literals in `requiredContexts`. A missing trace timestamp leaves the reporting date explicitly unknown; file/Git attribution retains its actual provenance and commit time without inventing message or fact time; stable methods independent of historical status need no added date. This prompt requirement does not make date attribution a deterministic semantic check.

Object mentions are a separate identity-navigation obligation. Their permitted scope is the complete exact source window bound by the segment, not only the cited excerpt or quote. A supported mention elsewhere in that same sourceKey may provide navigation; it neither repairs missing claim evidence nor permits another sourceKey or title-only identity. Ordinary repeated names need not all become mentions, but necessary identity occurrences remain inspectable. Optional derived typed evidence may only reuse the cited source ranges of its referenced body segments. Source matching/localization and source-faithfulness judgment remain different checks.

## 4. Corrections and knowledge revisions

Entity correction appends an immutable entity-analysis revision under exact generation/head and idempotent request identities; it does not rewrite body. Existing mention identity cannot move to another source span. Source-supported `new:` identities are host-assigned UUIDs; component/collection/candidate references must remain closed.

Body revision accepts a complete new `KnowledgeDraft` with inline evidence. The host rereads every referenced snapshot/version and validates exact UTF-16 quotes before appending. The old `citationLocators`/`--citations` and parallel grounding fields are replaced. A new body revision gets its own digest, remains pending and does not inherit retain; older projection refs become stale.

`apply-associations` pins exact body/digest, catalogs and association generation, creating a pending projection without source-coverage approval. `review-associations` reviews that projection only. Model `rebuild-associations` requires an exact active `sourceCoverageDecisionRef`, taking the full SourceSet from its coverage record rather than surviving body citations, without generating bodies. After revision, `prepare-source-review` checks new bodyRefs against complete original sources and records a fresh actual decision. Endpoints remain catalog/revision/entity-qualified, without name-based cross-window merging.

## 5. Domain and runtime boundaries

Knowledge contracts/history remain pure core; extraction owns phase wires and structural admission, application orchestrates use cases, and filesystem/executor adapters own effects. CLI and Studio use the same body-first flow. Cross-window entity-link execution remains independent.

Each stage records complete sources, prompt/profile/wire, system/input, producer and request digest before dispatch, checking execution/archive capacity first. Ledger, body, coverage and association have separate native identities and complete executor JSON (or bounded exception observations), archived before decoding. Refusals, partial failures, unknown fields, tool diagnostics, usage/cache and reported flags remain preserved, not represented as an old single run5 response.

Preparation is zero-model; confirm each exact requestDigest independently. Association additionally requires an active nonconflicting actual Agent/human coverage decision, rechecked at preparation and under the shared claim lock. Model all-covered/no-findings never approves itself. Revocation after claim preserves the sent original and pending result with invalidated context. Derived failure never deletes bodies. Stages default to 300 seconds with no automatic retry/reask/fallback, without implying cost or quality guarantees.

Journal4/default input2 binds the complete delivered sources and pinned ledger/body context. Association independently retains its v1 input envelope. RawUnits, host sourcePath/cwd and capture time stay local. Instructions in sources are data, not authority to expand reading or invoke tools. Metadata quotes remain metadata, never fabricated excerpt speech. Unreported usage/cost stays unknown.

## 6. Current storage contracts

Current physical paths and identities are defined by the [explicit workspace contract](../shared/storage-layout-spec.md#explicit-knowledge-workspace): body history Schema 3, independent association history Schema 2, entity history Schema 2, independent reviews Schema 1 and generation journal Schema 4, plus source-ledger/coverage histories Schema 1. Each body revision has `bodyDigest`; inline evidence is the source binding, without old parallel grounding/extractionRunId read dependencies.

`generation-journals/<run-id>.json` records phases and fixed publication intents. Originals at `generation-journals/outcomes/<run-id>/<invocation-id>.json` bind their request and complete byte digest. With current generation profiles, `resume` attaches held/orphan originals and replays exact commands/receipts with zero model calls. Partial publication retains fixed IDs and committed prefixes. A claimed phase with no original remains unknown and cannot be resent automatically. A never-claimed association may be sent only by explicit continuation. Repeating a completed run identity makes zero calls.

An active journal containing an older generation profile, including association v7 in prepared/claimed/archived states, is `unsupported`: the current build neither decodes archived output, attaches orphan output nor dispatches a later stage under mixed identities. Use the preserved matching build for recovery. Already recorded `prepared_writes` can replay their fixed publication intents without model decoding or calls; if further old-profile work remains, the run then returns to `unsupported`. Terminal completed/failed journals and their original bytes remain inspectable, and existing current-format body/entity/projection data remain readable. Historical records are never rewritten to claim the new profile.

Entity histories keep their 1,024-revision/16-MiB per-file limits and idempotent receipt replay; old revisions are not truncated. Catalog scans remain bounded at 4,096 files/64 MiB and report unreadable analyses separately. Structural validation, exact location and successful reopening do not establish semantic quality.

Current readers reject old typed knowledge v2 and current journal recovery rejects journal3 and run5. Old run inventory is explicit unsupported. [Migration](../knowledge/knowledge-domain-model.md#body-migration) requires a separate new workspace and preserved originals, creates new pending body revisions without retain inheritance, and does not retarget library/carrier refs. Old source/workspace/binary can be retained for rollback; there is no dual canonical reader.

Standalone `study` inspection/portable archive replay and `seal-run`/`sealed-runs` archive dispositions keep their independent historical identities; they do not restore old default generation or grant semantic acceptance. Current builds explicitly reject old typed generation plans with zero calls. Explicit sealing preserves raw inventory before its own disposition marker; it is not a migration or current journal resume.

Writes share `.knowledge-write.lock`; only a local owner proven exited permits lock recovery. Body reading remains available if its derived association or source is unavailable, with explicit diagnostics rather than a healthy-empty result.

## 7. Quality and completion evidence

Functional verification covers independent entity results, inspection/correction, shared knowledge identities and exact revision bindings, empty/partial/interrupted behavior, and rejection of unsupported formats. The [historical typed evaluation protocol](./entity-extraction-evaluation.md) owns its frozen criteria, corpus/checker identities, comparisons and review gates. It does not certify this body-first workflow; body source-faithfulness and real task use need separately bound evidence. Location and reference closure establish structure, not semantic accuracy, truth or reuse benefit; workflow tests cannot replace that protocol.
