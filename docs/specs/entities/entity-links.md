# Cross-window entity review journal

This is the additive domain foundation for cross-window association. The local application can retrieve candidates, preview bounded input, archive an already captured model response, record an explicit human decision, and recover organization publication. CLI, Studio review, a model executor, a governed proposal prompt, and real-model quality acceptance are not connected by this batch. It does not complete the end-to-end cross-window workflow.

## 1. Identity and candidate boundaries

`entity-link-retrieval/v1` applies NFKC, lowercase, and whitespace removal to current entity labels and source mention surfaces. Exact equality retrieves entities from other analysis windows; it never establishes identity, changes an entity UUID, or rewrites knowledge. More than 100 matches fails explicitly; unreadable analyses are reported separately. Unreadable library owners or review files fail the query rather than appearing as an empty healthy catalog.

A preview pins two distinct analysis windows, their entity UUIDs, entity revision IDs and generations, source snapshot/version, selected mention IDs, and each current library owner including its generation/head. An entity can be unowned, or one side can already belong to one library object. Two already owned sides require separate organization maintenance; previews refuse both same-owner and competing-owner pairs.

`entity-link-model-input/v1` includes those bindings, each selected entity, its selected saved mention evidence and analysis limitations. It excludes native paths, raw trace envelopes, and unrelated full source text. Canonical UTF-8 input is limited to 256 KiB; callers must choose fewer mentions rather than silently truncate evidence. Preview requires current, readable, position-matched evidence. Preview does not reserve a model execution or archive its input before a call; a future executor must implement its own durable preparation and usage lifecycle.

## 2. Independent v1 storage

`entity-links/<review-id>.json` uses `storeKind: entity-link-review-history`, `schemaVersion: 1`. This new namespace does not migrate or change entity history v2, extraction run v4, knowledge history v2, or library v1. Unsupported versions have no compatibility reader. Existing extraction prompt identities and bytes remain unchanged.

The immutable capture contains both endpoint bindings, input digest, request identity, exact raw output, declared executor/model and prompt version/hash, duration, and optional token/cost observations. `record()` verifies the input digest against the retained exact analysis revisions, including old revisions after a correction or source tombstone. Current head/owner changes do not discard a completed response. The response is limited to 512 KiB of UTF-8; an oversized capture fails before creating a review. Declared model/prompt metadata is archival provenance supplied by the caller, not proof that this foundation executed that model or verified prompt bytes.

The v1 model response has `responseKind: entity-link-suggestion`, `schemaVersion: 1`, both entity IDs, `assessment` (`same_object`, `different_objects`, or `insufficient_evidence`), side-specific supporting mention IDs, and a rationale. Admission checks structure and the exact selected entity/mention references. Invalid output remains verbatim with `invalid_response`; it can be rejected but cannot be accepted. Structural admission does not verify semantic identity or accuracy.

The unordered pair key binds both analysis/entity/revision and snapshot/source-version identities. Owner state and mention subsets do not reset rejection. Rejected exact revision pairs are suppressed from future preview/recall; a new entity revision may be reviewed again. Captures already in flight can still be archived: a later capture for a rejected or pending pair stores `duplicateOf` pointing to the earlier review and cannot publish organization changes. Such evidence-only duplicates do not block a new preview after the authoritative review conflicts. Recording the same review/request/content is idempotent; reused identities with changed content fail explicitly.

A review has at most three append-only events: `recorded`, `reviewed`, and an optional `applied` or `conflict`. SHA-256 belongs to the host; pure pair-key/history functions receive an explicit hash port and raw response limits count UTF-8 bytes with a pure encoder. Generation equals event count; head, request/event uniqueness, command digests, admitted response, exact intent endpoints and receipt identity are validated on reads. Files are limited to 4 MiB, the namespace to 4096 files and 64 MiB, without silent pruning. Pending intents reserve 4 KiB for their bounded terminal event within file and namespace limits. Writes publish JSON atomically; corrupt, redirected or unsupported storage fails closed and preserves existing bytes.

## 3. Human decisions and organization

Only a human actor can record or decide reviews. `accept` requires explicit `identityConfirmed: true` and a nonempty reason. It may override any structurally admitted model assessment, including `different_objects` or `insufficient_evidence`; the original recommendation remains visible. This expresses a human organizational decision, not a new model-quality score or proof that a knowledge claim is true. `reject` appends the human reason and leaves original entity UUIDs, analysis, knowledge, and library unchanged.

For a new library object, `accept` can supply `objectLabel` of at most 256 characters. Otherwise the complete left entity label is used only when within the library limit. A longer name requires explicit human naming; it is never truncated. Existing object labels are maintained through the existing library workflow. The chosen label and reason bind the decision digest and stable application intent.

Acceptance links the two original entities through the existing knowledge library. It creates a new library object when both are unowned, or appends to the one pinned owner. Unrelated existing members remain unchanged. It never merges source UUIDs, transfers members between competing owners, copies knowledge bodies, or treats chronology as truth. Both entities must have a proposed identity at the same referential level, which must also match the pinned existing owner’s fixed level; unresolved or incompatible identities require source correction before a new review.

## 4. Publication, conflicts and recovery

Human acceptance first persists one stable library command: request ID, object/revision IDs, author/time/reason, complete draft, and expected library head/generation. It then attempts publication. Entity-link transitions and library publication use the same `.knowledge-write.lock`; both endpoint source/entity heads, exact mention positions and owner generations/heads are checked inside that lock, including an unchanged member already present in the owner. An external precheck followed by ordinary library save does not satisfy this boundary.

Known source/entity, unresolved identity, owner, stale library and duplicate-pair conflicts append an explicit terminal conflict. An existing owner’s referential level remains fixed even if a source entity is later corrected; incompatible intent or recovery ends with `identity_unresolved`. Known prepublication library write capacity rejection (256-revision history, file or namespace) ends with `library_capacity`; an existing matching receipt is resolved before the history limit is checked. Review intent capacity is checked before persisting the decision, with terminal space reserved. A library listing/read capacity failure, corrupt data or unknown I/O error does not prove publication was rejected and remains retryable rather than becoming a capacity terminal. They do not publish a partial organization or undo history. A new review must be based on current bindings after the underlying problem is resolved. Two different existing owner objects are never automatically merged.

Review and library files are not a multi-file filesystem transaction. An unknown I/O failure leaves the durable accepted intent pending and retryable. If library publication committed but its acknowledgement or review append failed, `resume()` reuses the exact command; an existing matching library receipt wins before current source revalidation. This records the already committed fact without adding another library revision or calling a model. Before any publication, stale bindings still conflict. A terminal result is idempotent; a rejected review cannot be reversed or applied by resume.

The journal retains selected mention text and raw output as user data even after source deletion, without restoring a deleted source or allowing a new application from unavailable evidence. Deleting a source is not deletion of independently retained entity or review history. These files need the same privacy and backup handling as the selected knowledge workspace; they are not repository assets.
