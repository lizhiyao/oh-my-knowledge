# Cross-window entity review journal

The local application retrieves candidates, previews exact bounded input, durably prepares one explicitly confirmed invocation, executes the current production API adapter, archives its complete returned result, records a separate human decision, and recovers library publication. The governed prompt and request bytes are pinned. The CLI and [Studio review surface](../studio/studio-entity-links.md) expose this workflow; real-model quality acceptance remains pending.

## 1. Identity and candidate boundaries

`entity-link-retrieval/v1` applies NFKC, lowercase, and whitespace removal to current entity labels and source mention surfaces. Exact equality retrieves entities from other analysis windows; it never establishes identity, changes an entity UUID, or rewrites knowledge. More than 100 matches fails explicitly; unreadable analyses are reported separately. Unreadable library owners or review files fail the query rather than appearing as an empty healthy catalog.

A preview pins two distinct analysis windows, their entity UUIDs, entity revision IDs and generations, source snapshot/version, selected mention IDs, and each current library owner including its generation/head. An entity can be unowned, or one side can already belong to one library object. Two already owned sides require separate organization maintenance; previews refuse both same-owner and competing-owner pairs.

`entity-link-model-input/v1` includes those bindings, each selected entity, its selected saved mention evidence and analysis limitations. It excludes native paths, raw trace envelopes, and unrelated full source text. The actual system plus canonical prompt UTF-8 input is limited to 256 KiB; callers must choose fewer mentions rather than silently truncate evidence. Preview requires current, readable, position-matched evidence. Preview does not reserve or execute a model. A separate prepare command requires explicit content/model confirmation, binds the exact request and invocation budget, and rechecks source/entity/owner heads under the workspace lock.

## 2. Independent v1 storage

`entity-links/<review-id>.json` uses `storeKind: entity-link-invocation-history`, `schemaVersion: 1`. It replaces the unpublished offline `record(capture)` protocol; there is no compatibility alias or second reader. Entity history v2, knowledge history v2 and library v1 remain unchanged. The independent extraction-run v5 upgrade and its legacy-run boundary are owned by the [extraction specification](./entity-extraction.md); it does not change this v1 journal. Unsupported storage fails closed.

Preparation stores both pinned endpoint bindings, the exact governed system/prompt and JSON Schema, prompt/schema hashes, model/executor/output/timeout settings, confirmation digest, retry predecessor and a trusted concrete producer capacity witness. The request digest proves exact request integrity; it does not assert full runtime or credential identity. The actual API builder and executor share one frozen environment; beforeDispatch compares the actual endpoint/body with the prepared witness. No credentials are persisted in the witness. A zero-I/O inspect exposes the nonsecret producerContext during preview, and producerContextDigest participates in content/model confirmation. Endpoint or proof-context changes between preview and prepare fail explicitly. The shared PreviewSchema checks that displayed input matches the plan and returns stable reviewId, prepare requestId and startRequestId.

The unordered pair key binds analysis/entity/revision and snapshot/source-version identities. Name normalization only retrieves candidates; owner changes, mention subsets and side order cannot bypass a human rejection. One workspace may hold one prepared/running invocation. Failed or unknown invocations require an explicit retryOf and renewed confirmation; an active predecessor cannot be retried. Each confirmation authorizes one OMK invocation, whose internal attemptCount is recorded separately.

The append-only lifecycle is prepare → start → execution_recorded → reviewed → application_applied/application_conflict, with optional proven-owner-exit execution_unknown before recording. A prepared invocation can cancel_before_start. At most six events are permitted. Only the successful CAS start publishes dispatch_once; start acknowledgements, list/read/resume and ordinary reload never dispatch. A start written before a crash may already have been sent, so it consumes the slot even when no result exists. Only a proven exited local PID can mark a running owner unknown; age, remote hosts and missing locks are insufficient. Unknown and post-start cancellation never refund or automatically resend.

The complete returned JSON ExecResult is saved before structural admission, including failed partial output, refusal, executor-normalized token/cache counters, usage reported flags, stop reason, failure metadata and extra returned JSON fields. These are executor observations, not a claim that the provider explicitly reported each normalized zero. Unknown exception values are never JSON-stringified or inspected through getters/proxies: a bounded exception-diagnostic/v1 observation records unknown outcome/usage. The one archived outcome is immutable. An unarchived unknown can later save the original recovered result; an archived exception cannot silently be replaced by a second outcome.

The v1 suggestion remains entity-link-suggestion/v1 with same_object, different_objects or insufficient_evidence, exact entity/selected-mention references and rationale. Failed execution, observed tools, invalid JSON/references, token aggregate overflow or reservation overrun cannot be accepted. Original returned counters/output/refusal remain intact; finite negative durationMs observations caused by a wall-clock rollback are archived unchanged rather than corrected for storage. Structural admission does not measure semantic accuracy or establish identity.

API capacity comes from executable producer code, not caller-supplied numbers: a 4 MiB raw HTTP cap, nonfatal UTF-8 replacement up to ×3, three retained output/refusal/stopReason string channels, JSON UTF-8 escaping up to ×6, the inner diagnostic limit and actual frozen credential replacement growth in the outer redactor. Duplicated refusal fallback is included. A bounded fixed-field template covers the rest of the API result/envelope. Codex has no complete trace-derived bound yet and is rejected before preparation with zero dispatch. This does not disable the proven API path.

The product quota is 4096 files and 512 MiB per file/namespace, not an assertion about producer output size. Preparation reserves its proven complete outcome plus five future event slots, each bounded by an explicit maximum command/facts template (including 256 library members, 64 mention IDs, JSON escaping and human decision fields). Recording releases unused outcome capacity while retaining human/terminal space. Intent capacity is checked before recording a human decision. Compact canonical JSON publishes atomically with exclusive creation or CAS replacement; existing identical acknowledgements win before quota checks. Corrupt, redirected, unsupported or unreadable storage is never a healthy empty catalog.

## 3. Human decisions and organization

Only an explicit human actor can authorize preparation or decide identity; execution events record the host actor. `accept` requires explicit `identityConfirmed: true` and a nonempty reason. It may override any structurally admitted model assessment, including `different_objects` or `insufficient_evidence`; the original recommendation remains visible. This expresses a human organizational decision, not a new model-quality score or proof that a knowledge claim is true. `reject` appends the human reason and leaves original entity UUIDs, analysis, knowledge, and library unchanged.

For a new library object, `accept` can supply `objectLabel` of at most 256 characters. Otherwise the complete left entity label is used only when within the library limit. A longer name requires explicit human naming; it is never truncated. Existing object labels are maintained through the existing library workflow. The chosen label and reason bind the decision digest and stable application intent.

Acceptance links the two original entities through the existing knowledge library. It creates a new library object when both are unowned, or appends to the one pinned owner. Unrelated existing members remain unchanged. It never merges source UUIDs, transfers members between competing owners, copies knowledge bodies, or treats chronology as truth. Both entities must have a proposed identity at the same referential level, which must also match the pinned existing owner’s fixed level; unresolved or incompatible identities require source correction before a new review.

## 4. Publication, conflicts and recovery

Human acceptance first persists one stable library command: request ID, object/revision IDs, author/time/reason, complete draft, and expected library head/generation. It then attempts publication. Entity-link transitions and library publication use the same `.knowledge-write.lock`; both endpoint source/entity heads, exact mention positions and owner generations/heads are checked inside that lock, including an unchanged member already present in the owner. An external precheck followed by ordinary library save does not satisfy this boundary.

Known source/entity, unresolved identity, owner, stale library and duplicate-pair conflicts produce explicit accepted_conflict terminal facts after the human decision. An existing owner’s referential level remains fixed even if a source entity is later corrected; incompatible intent or recovery ends with `identity_unresolved`. Known prepublication library write capacity rejection (256-revision history, file or namespace) ends with `library_capacity`; an existing matching receipt is resolved before the history limit is checked. Review intent capacity is checked before persisting the decision, with terminal space reserved. A library listing/read capacity failure, corrupt data or unknown I/O error does not prove publication was rejected and remains retryable rather than becoming a capacity terminal. They do not publish a partial organization or undo history. A new review must be based on current bindings after the underlying problem is resolved. Two different existing owner objects are never automatically merged.

Review and library files are not a multi-file filesystem transaction. An unknown I/O failure leaves the durable accepted intent pending and retryable. If library publication committed but its acknowledgement or review append failed, `resume()` reuses the exact command; an existing matching library receipt wins before current source revalidation. This records the already committed fact without adding another library revision or calling a model. Before any publication, stale bindings still conflict. Archive I/O failures retain a stable execution identity and in-process raw outcome for resume; after process loss without saved bytes, the state remains running/unknown rather than issuing a fresh request. Filesystem atomic publication does not promise power-loss durability or remote exactly-once delivery. A terminal result is idempotent; a rejected review cannot be reversed or applied by resume.

The journal retains selected mention text and raw output as user data even after source deletion, without restoring a deleted source or allowing a new application from unavailable evidence. Deleting a source is not deletion of independently retained entity or review history. These files need the same privacy and backup handling as the selected knowledge workspace; they are not repository assets.
