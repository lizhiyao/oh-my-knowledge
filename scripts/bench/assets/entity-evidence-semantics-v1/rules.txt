

以下是实体身份与集合表示的局部语义澄清。仍执行上述实体、原文提及和可复用知识的完整联合任务，按上述同一 wire Schema 返回 knowledge-extraction／schemaVersion=4。proposals 仍按来源和可复用性判断，不要求为空；其它范围、精确定位、引用闭合及知识证据规则不变。

先区分所指对象，再填写身份字段，不按名称、复数词、数值或路径猜层次。下列合成成对示例只说明判断与已有字段的表示要点，不是本次待分析材料，也不是完整响应模板；实际输出仍须包含同一 Schema 要求的全部字段，不带入示例对象。

一、集合主体与成员完整性分别判断。
来源把若干对象作为一个共同范围独立讨论时，该范围是 collection，不因成员未列出而改成 object 或抹去该范围。知道是哪一组而不知道成员时，可使用 identityStatus=proposed、collection.completeness=unknown、memberEntityIds=[]，在 uncertainties 说明成员缺口；collection.mentionIds 至少引用该集合的一处实际提及，rationale 说明共同范围及成员依据。部分成员有据时用 partial 并只列这些成员，不补占位实体，不把数量当作成员身份。若连所指的组也无法确定，才保留 unresolved 集合及未知成员；身份未知与成员不全不是一回事。
抽象类别与单一制品也可使用 object，不能因为类别可有多个实例，或一个制品包含多部分，就机械建立 collection。集合、类别和制品是否分别成立仍取决于来源独立讨论的对象；数量词、复数形式及“套”“册”等字样都不是分类器。
合成对照 A：来源“本次封存的七张岩样卡作为一组核验，单卡编号未记录。”指向本次封存的卡组；保留 proposed 的 collection、unknown 成员、空 memberEntityIds 及缺口理由，不虚构七个成员，也不因成员未知改成单卡 object。来源改为“岩样卡是一类记录载体，本次只讨论这一类的定义。”时，所谈类别可为 object，不凭潜在实例补集合。
合成对照 B：来源“《砂纹册》是一份登记册，本次单独核对它的封面说明。”讨论一个制品，可为 object，不因册内有多页改为 collection。来源改为“本次封存卡组包含 R17 和其它编号未记录的卡；另行核对 R17 的背面。”时，卡组可为 proposed 的 collection、partial 成员，只列有据的 R17，并为 R17 保留自己的提及；不能把集合提及重复分给成员。

二、规范接口、具体实现与加载入口按来源的身份关系判断。
实现某接口、兼容其行为或作为替代入口，不等于与接口或其它实现是同一对象。来源分别独立讨论接口和实现时分别保留；来源明确入口只是同一实现的另一名称或定位时按该对应判断，不机械再拆一层。没有独立讨论或对应依据时，不为每个名称强造“接口／实现／入口”三层，也不凭常识补规范名称、作者或自写归属。component 仍须有上述来源职责依据；componentRef 仍只用于 instance／version，不能拿它表达“实现某接口”。
逐处核对名称在这里指向什么：明确讨论标准接口时不以某个实现代替；明确指向实现时不因共用接口名而归给标准接口。只知道某个已指明对象、但不知道作者、类型或入口关系时，保留该对象及具体未知，不能在 description 或 rationale 先写“自写”再用 uncertainties 抵消。某处确实无法确定所指时保留局部 unresolved、缺口理由和有据候选；候选仍须满足上述同层次规则，不凭同名自动关联，也不用抽象接口掩盖明确的具体所指。
合成对照 A：来源“规范接口 RouteLedger 定义读取条目的契约；我们维护的模块 PebbleLedger 实现此接口；./ledger-entry 只是 PebbleLedger 的另一个导入入口，不是另一份实现。”支持接口与实现分别保留；来源已给出模块职责，PebbleLedger 可为 component，路径提及按明确入口对应绑定该实现，不再虚构一个独立实现。
合成对照 B：来源“现有读取模块 ClayReader 与候选入口 ./route-reader 分别参加比较；记录没有说明两者是否指向同一实现，也没有说明候选入口的作者。”支持分别被指向的对象，不能把路径归给 ClayReader 或写成自写实现；保留作者及对应关系未知。来源没有独立讨论规范接口时，不从入口名补接口实体；未知关系不自动令两个已知对象都变成 unresolved。

三、未确认的候选不等于已撤回的猜测。
逐项检查 possibleEntityIds 的当前窗口依据，而不只检查目标名称是否出现。候选是有据的可能对应，不是已确认身份；未确认本身不要求删掉候选，也不能把候选直接当作确定所指。助手选择回答某对象、名称相同或共同出现均不自动确证原始含糊指代。
来源明确撤回某项猜测或对应依据时，结合撤回范围重新判断该候选关联。若它唯一的对应依据已撤回且无其它支持，不继续把它列作该含糊提及的有据 possibleEntityIds；保留原局部未知及撤回造成的依据缺口。被猜测的名称若本身仍符合实体范围，可以作为曾被提出的对象保留，其明确名称提及不等于与原含糊对象存在有效对应。若仍有独立来源支持该候选范围，保留那项支持及未决，不因出现“撤回”二字清空所有候选。不同说话者的冲突不按时间或角色自动裁决；具体撤回、澄清及剩余依据均按其来源语境判断，不超出窗口补结论。
合成对照 A：来源先说“这里的‘灯桥’是哪一种还不清楚”，随后有人说“我猜是灯桥检索器”，又明确说明“刚才仅凭同名猜测；这项猜测撤回，窗口内没有其它对应依据”。原“灯桥”仍 unresolved，possibleEntityIds=[]，uncertainties 说明依据被撤回；可以保留曾被明确提出的“灯桥检索器”及其猜测语境，但不保留失去依据的候选关联。
合成对照 B：来源说“这里的‘灯桥’只能指灯桥检索器或灯桥索引器，但不知道哪一个”，后文只是“尚不能确定”。保留 unresolved 的原指代及两个同层次 proposed 候选，不能将“未确认”当作“已排除”，也不能任选一个消歧。
合成对照 C：来源先明确“这里的‘灯桥’只可能是灯桥检索器或灯桥索引器”，后有人猜其中一个，再说“撤回我的二选一猜测，我没有选择依据；此前给出的两个候选范围没有被撤回”。撤回的是选择某一个的猜测，独立候选范围仍有据；保留两个 possibleEntityIds 及未决，不清空或强行选中。
合成对照 D：一位发言者说“灯桥在这里指灯桥检索器”，另一位说“我认为指灯桥索引器”，窗口没有可裁决依据。保留冲突、局部未知及有据的可能对应，不因后一句更晚便让它胜出；有明确且适用于该处的澄清依据时再按依据判断，不把纠正身份当作知识结果已经验证。

输出前在同一次响应内核对：集合的共同范围与成员缺口是否分开表达；接口、实现及入口的实体描述、限定和每处提及是否具有同一来源支持的范围；每条候选关联是否仍有未被撤回的对应依据；rationale 是否解释实际选中的那处原文而非另一处同名文字。保留真正无法消解的未知，不靠删去有据对象规避判断；在本响应内保持引用闭合，不把结构符合当作语义已经核实。知识陈述继续保留这些身份限制及来源证据，不以实体识别代替知识提炼。
