# AGENTS.md - OMK Project Conventions

> Chinese original and authoritative source: [AGENTS.md](./AGENTS.md) - where this twin and that file diverge, the Chinese file prevails. This file is the English companion for human contributors and covers only this root checklist; the per-directory `AGENTS.md` domain rule files are the machine-loaded instruction source and are maintained in Chinese only - see the boundary note under "Starting Work and Delivery".

OMK (Observe. Measure. Know.) observes and measures the version differences of prompt, RAG, skill, agent, and workflow by holding the model fixed and changing the knowledge artifact. All changes prioritize protecting measurement comparability, evidence integrity, and user data.

This file is the tool-neutral project onboarding checklist. Claude Code imports it through CLAUDE.md; do not copy and maintain a second set of project rules for different tools.

## Starting Work and Delivery

- When the work involves a commit, PR, branch, or release, read the relevant process in CONTRIBUTING.md; within the same task, reuse it once read as long as it has not changed.
- Before modifying a subdirectory, check the AGENTS.md files along the path from the repository root to the target file; the nearest file supplements or overrides the upper-level project conventions, and ordinary local tasks do not walk the rules of the whole repository. Only this root file has an English companion: nested per-directory AGENTS.md files stay Chinese, so read the Chinese file in that directory and do not expect an AGENTS.en.md beside it.
- At the start, briefly state the requirement, non-goals, affected boundaries, and risks; one or two sentences are enough for a low-risk change. Once the current task has a clear direction, keep moving under the existing authorization instead of repeatedly asking what comes next between the routine steps of implementation, verification, and autonomous CR.
- The user has authorized a default delivery chain for OMK changes: complete implementation, verification, autonomous CR, commit, push, and PR creation autonomously, and merge to main once the relevant gates and remote CI have passed and review findings have been handled per the definition of done, without asking for confirmation for each commit, PR, or merge. This authorization covers the current and all subsequent change tasks; explicit limits the user sets on a specific task - read-only, local-only, no commit, or no merge - take precedence.
- A release still requires separate authorization, and merging is never release authorization. The default delivery authorization does not expand the requirement scope, and it does not bypass the confirmation requirements for public-contract or existing-data changes, platform approvals, repository protection, or any other authorization boundary around high-impact operations.
- Replace the old implementation directly by default; do not keep compatibility layers, aliases, or dual-track branches for old entry points, old fields, or old behavior that no requirement asks for. When published public contracts or existing data are involved, state the impact and the replacement/migration plan first, execute only after the user confirms, and neither decide on compatibility on your own nor perform a destructive replacement outright; when the current task already records the decision, do not ask again. Necessary breaking changes still follow the versioning and migration requirements below.
- For long tasks, keep the existing execution checklist in the corresponding Issue/PR updated promptly, with status reflecting what has actually been completed.
- Test maintenance does both addition and subtraction: when adding or migrating tests, review the affected existing samples, delete assertions that are no longer valid or that only bind to implementation details that have been replaced, merge duplicated coverage, and prefer reusing and rewriting existing tests; never treat a growing sample count as a quality improvement, and never sacrifice coverage of key behavior and failure paths in order to reduce the count.
- Run clean-room verification only when a release, a packaging/install contract change, a real user entrypoint change, or a risk review explicitly requires it; do not repeat it while the trigger conditions, the boundary under test, and the evidence are unchanged.
- When you start Studio manually for the user to view, prefer the fixed port the user specifies and otherwise the CLI's default fixed port; do not pass `--port 0` on your own initiative. If the port is occupied, first identify the service already running, confirm it belongs to this task, and then reuse or restart it - do not switch to a random port unilaterally. Random ports are only for isolating automated tests or for scenarios the user explicitly asked for; the address you show still uses the `server.start()` return value.

## Development Feedback and Verification

This section is the single source of rules for what triggers verification and how its results are reused; for concrete commands and build dependencies see `CONTRIBUTING.md`, and for the review method see `CODE_REVIEW.md`.

- Search from the target files and their direct call boundaries, and widen the scope only as evidence requires; batch independent read-only operations. Reuse rules and evidence that have not changed, and do not re-read or scan the whole repository just because a new phase began.
- Each round of changes prefers `yarn test <测试文件...>` (the affected test file paths) and keeps the working-tree pollution check; use `yarn ci:quick <测试文件...>` when a phase closes and needs combined static checks. Do not bypass the isolated entry points by running Vitest directly, and do not require the quick gate on every round. Source tests may skip the build; tests that depend on dist, the real CLI, or Next production assets update those artifacts first - stale artifacts cannot prove new source code correct.
- Local verification is tiered by risk: ordinary local changes use `ci:quick` for targeted verification; changes spanning modules, dependencies, build/packaging, or CI gates must run the full `yarn ci` locally; when tests depend on compilation or production assets, update the corresponding build artifacts before testing. Before the first push, running the one tier that matches the risk level on the final change set is sufficient, and the full `yarn ci` is not appended unconditionally; when the risk tier is unclear, use the full gate. When the user explicitly asks for narrower verification, run that narrower set and record the boundaries left uncovered. `ci:quick` does not replace the full gate.
- After the first push, reuse the local results while the facts are unchanged and use remote CI as supplementary confirmation; complete later fixes in batches, re-run targeted verification or the full gate according to the affected scope, and do not treat remote CI as an incremental feedback loop. Record the commands, the changes under test, and the uncovered boundaries; when code, dependency, configuration, or environment changes invalidate old evidence, re-run only the invalidated scope.
- Wait for the process/CI handles you already started; do not relaunch them because observation timed out. Deliver once the requirement is met, the necessary verification has passed, and the review findings have been handled; without new evidence, do not repeat builds, a full CR, or clean-room verification.
- When concurrent work on the same machine must not interfere with each other (for example another piece of work holds uncommitted changes), that task uses one isolated checkout outside the repository and reuses it for later verification by default rather than opening a new one per phase; when a second one is genuinely needed, state its purpose, for example comparing against the pre-change baseline or a different dependency version. Destruction applies only to a temporary checkout that this task created, has no unsaved changes, has no running processes, and holds nothing the user still needs to view, and its registration is cleaned up along with it.
- Each checkout maintains its own writable build state bound to its own artifacts (incremental builds, type checking, and lint caches): sharing it lets a checkout that is missing artifacts falsely pass with exit code 0, and such build results cannot serve as gate evidence. Read-only package download caches are not in this category - they sit outside every checkout and stay shared. Symlinking dependency content per entry is only available when versions and install configuration match and the shared target is not being modified concurrently; otherwise that checkout installs on its own, and `CONTRIBUTING.md` documents the mechanism and the measured results.

## Autonomous CR and Definition of Done

- Changes that alter behavior, contracts, packaging, documented promises, or repository rules get one CR completed autonomously before the first push/delivery; purely mechanical changes get a quick re-check, with depth matched to risk.
- Before the first autonomous CR you must read [`CODE_REVIEW.md`](./CODE_REVIEW.md) in full; within the same task, reuse it while the rules have not changed and do not reload it. From a reviewer's perspective, inspect the final change, the direct call boundaries, contracts, and verification evidence read-only; when you find cross-module impact, widen the scope along the evidence. Use an independent reviewer when available, otherwise do a fresh-pass self-review.
- Resolve P0-P2 before delivery; resolve P3 or register a follow-up. After fixes, re-review the affected surface and re-run the affected verification; run a full CR again only when architecture or public behavior changes substantially, CI raises a new problem, a rebase conflict is significant, or external review raises a new high-risk direction.
- Finding evidence, priority, and format follow CODE_REVIEW.md. When there are no findings, say so explicitly and do not manufacture speculative issues; report gates, real user paths, and unverified scope truthfully, and never let green CI stand in for requirement completion.
- When the user asks for a review of a specific PR, publish the conclusions directly to that PR; when the user explicitly asks for a local-only review, do not publish, and when nothing is specified or the corresponding PR cannot be determined, do not guess a publish target.

### CR Runtime Artifact Isolation

- artifacts/cr/ and knowledge/cr/ are not source assets: never create or keep them inside the repository, and never hide them with .gitignore. A purely read-only review creates no intermediate files; only when a CR tool genuinely writes to disk at runtime do you use one unique temporary directory outside the repository to hold all of its runtime output, with the output path configured explicitly, and you never run a result sync that writes back into the repository.
- Check the working-tree state before and after CR to make sure the review tooling produced no extra pollution, and do not clean up or overwrite the user's pre-existing changes. Issue/PR/CI are the persistent review record; commit a report as a project asset only when the user explicitly asks.

## Code Review Rules

- Do not silently change the scoring measurement definition, statistical semantics, prompt bytes, Schema identity, or the persistence contract. Version necessary changes explicitly, and mark the corresponding BREAKING-*, migration, and measurement impact in the PR title/description.
- eval-core is the deterministic measurement kernel on the Node side: it does not depend back on the CLI, the filesystem, the network, environment variables, a concrete executor, or Studio. "Host-agnostic" refers to those external dependencies, not to the Node runtime itself - core uses `node:crypto` directly for canonicalization digests, does not make them injectable, and does not claim to run in a browser or edge runtime. Core expresses only pure contracts and deterministic transformations; side effects live in eval-workflows or the corresponding adapter.
- Preserve provenance, time, correlation identity, and raw evidence; derived views never overwrite raw evidence, and observed signals never masquerade as causal conclusions.
- Tests use an explicit temporary root and environment isolation, and cover the cleanup path after failure or interruption; production writes are persisted only where the public storage contract allows, never unilaterally into user directories or global state.
- New discriminant fields, or ones that are safe to rename, use qualified names such as eventKind and runtimeKind; bare kind stays reserved for Artifact.kind by default. Existing kind fields in public schemas that are already published, persisted, or externally consumed are not renamed in passing; a necessary rename is versioned on its own with the incompatibility stated explicitly, and no compatibility reader is kept for old versions - the Resolver recognizes only the current version, and being unable to read old documents back is the agreed strategy. See docs/specs/terminology-spec.md §5.4 for details.
- User-visible service URLs use the actual address returned by server.start(); do not hard-code ports.
- .agents/skills/omk/ is the single source of the official Skill and .claude/skills/omk stays a symlink to it; do not copy a second one. This file does not repeat the Skill user tutorial.

## Git and Writing

- main is the only long-lived branch; create short branches from main and merge them through PRs, never commit directly to main, and never restore a develop workflow. Releases also go back to main through a short-branch PR and are then triggered by a tag; see CONTRIBUTING.md for the process.
- A short branch name's prefix takes the Conventional Commits type of that branch's main change (`feat/`, `fix/`, `docs/`, `refactor/`, `test/`, `perf/`, `chore/`, `ci/`), stays consistent with the commit message's `type(scope):`, and is not tied to a tool, model, or person; when one branch carries several kinds of change, do not force an alignment.
- The commit format is type(scope): Chinese subject, where scope uses stable module names; this file uses agents-md.
- User-facing copy prefers Chinese, and Chinese text uses full-width punctuation; code, paths, commands, URLs, frontmatter, mathematical intervals, technical identifiers, and English technical parentheticals keep their own grammar. Conventional Commits' type(scope): prefix stays half-width.
- An LLM judge is always called judge (评委), never 判官. PR review comment language follows the language configured in the user's operating system.
- PRs are created non-draft by default; use Draft only when the user explicitly asks for a draft. Incomplete verification, known issues, and merge blockers are recorded truthfully in the PR description, and the PR may still only be merged once the gate and the definition of done are met.
- The PR boundary is set when the work is divided at the start, not closed out only at the autonomous CR stage; the only complete statement of this measurement definition is in CODE_REVIEW.md under "Keep the work reviewable while implementing".
- A PR describes user impact, migration, and measurement limitations and links the relevant Issue/predecessor PR; do not pile up line numbers, test checklists, or nested implementation details that the diff already shows.
- When a reply references a remote object (PR, Issue, commit, Actions run/job, document, local service address), give the clickable URL in the same sentence; take the URL from an existing field in the CLI output instead of constructing it yourself, and if it is not available, write only the name.
